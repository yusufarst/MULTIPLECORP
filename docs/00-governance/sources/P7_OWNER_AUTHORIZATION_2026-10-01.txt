- The two missing durable items:

9.2 Decide and document. The settlement must define:
a) The durable record shape:
   - the kind or record name;
   - the typed columns QS-14 needs: actor, both sides' entity types and
     public ids, the companies concerned, detection time, correlation
     and command ids;
   - LG-03 redaction; no file contents.
b) Lifecycle and retention, and whether each item is a notice (it ages
   out, or stays within a window) or carries a review state. A review
   state:
   - is Owner-only;
   - never gates, blocks or alters any business fact or command;
   - never becomes a stored queue of business truth.
c) How the item enters QS-14: register row, typed source, index and
   budget.
d) The write path:
   - which request writes it, when, and whether inside or outside the
     business transaction;
   - its effect on locks, which must be none out of order;
   - what happens if the write itself fails. The actor's outcome never
     changes; state the residual.
e) Owner-only visibility. The item never appears:
   - on either record's timeline (PJ-11);
   - in Admin lists, search, exports or notifications;
   - in any security-log view available to Admins.
f) No information oracle for the submitting user:
   - response, wording, timing class and later visible state are
     identical whether or not a hidden match exists;
   - for a batch, exactly DP-18's wording and nothing more.
g) Rejection semantics preserved: every outcome stays exactly as
   approved.
h) P6 transaction and concurrency semantics preserved. If a refusal path
   must commit the record, state how it relates to D-CC-05 and SQ-23 and
   add the minimal clause.
i) The P8 proof obligation: a handoff that extends H8-12.
j) GAP-034's status: it stays OPEN with a P7 continuation note — design
   settled, runtime proof in P8 — unless repository evidence standards
   allow otherwise.

F. Command interaction model (HO-01–HO-10; ARCHITECTURE §10; WORKFLOWS
   §1)
   1. Five user-visible response states. Keep the distinction between
      recorded outcomes and transport or FAILED conditions.
      - COMMITTED.
      - REJECTED, with the failed precondition in business terms.
      - CONFLICT, with the current state.
      - PENDING, for background work only.
      - FAILED: "could not be confirmed". Repeating the same
        `command_id` is safe. A background FAILED means the committed
        action stands.
      The non-outcome answers are each presented distinctly:
      - the AZ-11 denial, identical to not-found (WS-10);
      - 401/419;
      - validation errors;
      - network loss.
   2. `command_id` lifecycle:
      - one per intent;
      - reused for every automatic and manual retry until a terminal
        outcome;
      - kept across re-authentication for a submission that may have
        reached the server;
      - newly minted after a terminal outcome, after the payload
        changes, and for a form that was never sent;
      - a refused intent is remembered (CI-06), so a corrected request
        is a new intent.
   3. Double-submit (HO-03): a disabled control is a convenience only. A
      new visit may interrupt the old one while the server completes it,
      so the screen shows the recorded outcome.
   4. Stale state and CONFLICT (HO-04; ST-01–ST-09):
      - show the current state, keep the input and offer re-apply;
      - a stale count leads to a recount;
      - a changed Force Complete snapshot is shown again;
      - "already recorded" (the CI-05 replay table, or SQ-07 after
        expiry) is presented as "sudah tercatat — periksa sebelum
        mengulang", never with a re-apply.
   5. Duplicate confirmations (HO-05):
      - L-49;
      - the payment override with a reason, for an ADM+ actor (BD-02);
      - in-scope FL-10 and L-45 evidence warnings (H7-07).
      Each is a second, explicit submission that names the matches it
      acknowledges.
   6. Background requests are marked (HO-06; RB-05; RV-06). A download
      is not background.
   7. Retry after FAILED keeps the same `command_id` (HO-07). Lock-wait
      FAILED copy reflects TX-01–TX-10: safe to repeat.
   8. Business date (HO-08; ST-08):
      - an explicit field on every command form, prefilled from the
        server's day (WIB);
      - the screen says whether the user chose it;
      - a prefilled date that is no longer today returns CONFLICT for
        confirmation;
      - backdating is visible, and the numbering period follows the date
        (NM-05);
      - the pattern is compact, not a heavy field.
   9. Exports (HO-09; H6-04; JB-03):
      - requested, pending, ready, failed and WITHHELD states in the
        requester's own list;
      - at most two in progress per account;
      - the row bound is refused with a request for a narrower period
        (PF-28);
      - downloads are ordinary browser requests;
      - a withheld download answers as AZ-11.
   10. Lists, search and scanner (HO-10), per section 10-I.
   11. A screen may sequence several commands. It presents each outcome
       separately and never implies that they commit together.
   12. Money and quantities:
       - entered and submitted as decimal strings exactly as typed;
       - no binary floating point;
       - authoritative totals, availability, outstanding and credit are
         server values;
       - any client-side preview is labelled provisional or fetched from
         the server.
   13. Routed refusal (SQ-23): the actor is told that the Owner, or an
       actor with the grants, will see it (HO-01; QS-20).
   14. A replay by another account is CONFLICT without disclosure. A
       deactivated account is answered as unauthenticated (M-13).

G. Session, expiry, re-authentication and unsent input (AU-07; H7-05;
   H7-12; H7-13; HO-02; WF-ACC-01)
   - 60-minute idle and 12-hour absolute timeouts. Warn before idle
     expiry with a user-initiated "stay" action. Background requests
     never extend a session.
   - Distinguish two cases:
     - a form never sent: after re-authentication it is a new intent,
       and stale checks apply (WF-ACC-01);
     - a submission whose response is unknown: the same `command_id` is
       reused (HO-02).
   - Never write form payloads, S3/S4 values or identifiers of
     out-of-scope records to localStorage, sessionStorage, IndexedDB or
     Cache Storage (WS-07, WS-08).
   - Expiry, termination and login responses clear Inertia history and
     client caches, or reload the whole document (H7-12).
   - Design how unsent input and a pending `command_id` survive an
     in-place re-authentication in memory, without violating H7-12.
     Verify the documented Inertia behaviour and record the evidence.
   - Where preservation is impossible (absolute timeout, termination,
     logout, full reload), warn before the loss. Never lose input
     silently.
   - If no documented mechanism satisfies both HO-02 and H7-12 without
     browser storage:
     - choose the safest documented alternative;
     - record the residual as a gap;
     - never weaken a SECURITY control. Weakening one is a STOP

   - Credential-link pages (H7-04).
   - Generic authentication messages (H7-01).
   - First-login and credential-event notices (H7-14).

H. Numbering UX and company onboarding (HO-39; NM-03; NX-01; NX-13;

   2. Start and seed confirmations:

   3. The scheme form and its refusals explain:

      - the earliest date a new scheme may take effect;
      - a same-day scheme splits that day's documents between two

   4. Refusals explained:
      - a start is refused while a batch that is not ABORTED holds VALID

      - start and seeds are unavailable before go-live is recorded.

   5. Company onboarding is a sequence of separate commands:
      - company master;
      - identity assets and bank accounts, with step-up;
      - numbering schemes;
      - the numbering start per type, PROJECT included;
      - Admin grants.
      Readiness is derived from state, never stored progress (WORKFLOWS
      §1). The screen makes clear that nothing of a type can be numbered

   6. C-10 refusal UX for Admin users:
