3. POST-INCIDENT RECOVERY DESIGN
==================================================

This section replaces the recovery order written into AU-21, AU-14, H8-21,
H9-07 and H9-14 for R3-01 and R3-13.

3.1 Terms
- Compromise window: from the suspected start of the compromise to the end
  of the incident command. The operator records its start, as established
  with the Owner, in the audit event of every recovery step. If the start
  cannot be dated, it is the creation time of the leaked key in the dated
  key register.
- Pre-window Owner: an account that held the OWNER role and was active at
  the start of the compromise window.

3.2 Which scenario applies
- Scenario A applies only when P9's inventory excludes write access by the
  attacker to the database and to the server. Only then is the audit trail
  authoritative (RG-11) and the in-application path below used.
- Otherwise, Scenario B applies.

3.3 Scenario A — order of recovery
1. The incident command completes, protocol (a)–(d).
2. For each pre-window Owner whose OWNER role or active flag was removed
   during the window, as the audit trail shows, the operator verifies the
   person in person and runs the OWNER-restoration command (3.5).
3. The operator recovers each pre-window Owner through AU-14, path (e). The
   person sets a new password and must enrol TOTP.
4. The recovered pre-window Owners review the accounts, roles, grants,
   credential links and Google links created or changed during the window
   (R2-03, R3-01). Then:
   - a confirmed account holding the OWNER role is recovered through AU-14,
     path (e), and loses its Google link;
   - a confirmed account activated during the window without the OWNER role
     receives a plain AU-12 RESET link;
   - for any other such account, the Owner removes the role or deactivates
     the account (RG-09, RV-04, RV-05).
5. Every other account receives a plain AU-12 RESET link (R-02, R2-10).
   Grants revoked during the window are restored through normal Owner
   commands.

3.4 Scenario A — when the in-application path stops
The in-application path stops, and the case is handled as Scenario B, when:
- no pre-window Owner can be established from the audit trail with
  certainty — for example, the window reaches back before every OWNER
  assignment, or an OWNER assignment has no audit event; or
- no pre-window Owner is available.
An account that first became Owner during the window is never restored,
recovered or promoted without the review of step 4.

3.5 The OWNER-restoration command (new, operator console)
- Usable only during incident recovery, after the incident command has
  completed.
- Only for a pre-window Owner whose OWNER role or active flag was removed
  during the window, as the audit trail shows.
- It restores the OWNER role and the active flag to the values the account
  held at the window start, and nothing else. It never:
    * creates a new Owner;
    * promotes an account that first became Owner during the window;
    * activates an account that was inactive at the window start;
    * sets a password, a secret or a credential link.
- It is not an NX-02 activation and issues no RESET link. The account's
  password is already unusable from the incident command; the person
  recovers only through AU-14, path (e), and must enrol TOTP.
- Each restoration writes an audit event carrying the operator's identity as
  AU-14 records it (RG-11 exception) and the recorded window start, and
  raises an alert under LG-07.
- It runs under the runtime role and under the account row lock. It adds no
  role, privilege, table or field.
- Agents never run it (SX-04). Operator abuse of it is the accepted K4 risk
  of TM-57.

3.6 Scenario B
- Scenario B means direct database or server write compromise, or any other
  condition in which in-application state and audit evidence cannot be
  trusted. No step of 3.3 runs.
- Recovery uses only a backup or snapshot that is independently verified as
  both predating the relevant compromise and trustworthy enough for incident
  recovery.
- The DIR-009 same-VPS backup is never presumed to be clean or trustworthy.
  DIR-009 remains an accepted V1 risk (RISK-001), and no document presents
  it as proof that a clean backup exists.
- If no such backup or snapshot exists, the in-application recovery path
  stops and the Owner takes an incident decision outside the application.
- P9 and P10 define the recovery runbooks.

3.7 Obligations
- P9/P10: the installation step that creates the first Owner account writes
  an audit event recording the OWNER assignment and the operator's identity,
  so the audit trail can establish every pre-window Owner.
- P9 weighs periodic rotation of the application key. Because the window
  cannot start before the leaked key was created, rotation shortens it when
  a leak cannot be dated.
