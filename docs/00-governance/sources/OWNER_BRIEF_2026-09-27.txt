- dispatch

- adjustment
- stock opname
- reversal

25. DATABASE LEAK ASSUMPTION
==================================================

Assume the application database could someday leak.

Passwords must remain password hashes only.

Use proper one-way password hashing.

Do NOT invent manual salt handling.

Argon2id/bcrypt already handle random per-password salt appropriately.

If considering a server-side pepper:
treat it as optional advanced hardening and keep it outside the database/repository.

Do not claim password hashing makes a database leak harmless.

Plan defense in depth.

27. RACE CONDITIONS
==================================================

Explicitly identify race-sensitive operations, including:

- stock dispatch
- stock receiving
- stock adjustment
- payment
- invoice issue
- document numbering
- project state transition
- financial state transition

Use:
- short DB transactions
- row locking where necessary
- atomic updates
- database constraints
- consistent lock order
- deadlock-aware retry where appropriate

Example required invariant:

Stock = 1

Two concurrent dispatch requests of quantity 1:

expected:
one succeeds
one fails
final stock = 0

NEVER:
both succeed
stock becomes -1

Plan automated concurrency tests.
