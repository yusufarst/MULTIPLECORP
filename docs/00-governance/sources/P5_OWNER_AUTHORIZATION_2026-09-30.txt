10. PLANNER NOTES — NOT OWNER DECISIONS
==================================================

These are pressure points identified by the planner. They are analysis
only. Verify each against the repository; the repository wins. They grant
no business authority.

PN-1 Role versus individual capability.
DATABASE §4.1 provides:
- roles → role_capabilities;
- user_capability_grants (ADM+);
- user_company_grants.

AC-13 needs individual Admins with and without inventory permission.
Resolve how one Admin can lack a capability without new launch roles or
custom-role management. Options include:
- the role acts as a ceiling, with per-user grants;
- a role baseline, with per-user optional bundles.

Planner preference:
- a new Admin has no company grant and no optional capability until the
  Owner grants it;
- OWNER_ONLY capabilities are never grantable to Admin.

Amend §4.1 only under section 13, if its approved text is otherwise
contradicted.

PN-2 Owning-company identity in physical views.
Three approved workflows need the actor to know whether units belong to
another company:
- WF-INV-07 inter-company authority;
- L-42 single-company confirmation;
- SF-UNATTRIBUTED recognition.

Planner assessment: exposing the owning company's identity (an S0 name or
code) for pooled units is the minimum necessary projection. This excludes
cost, supplier, prices and purchase or receiving references. It exposes
none of the nine protected categories, so it is Level 1.

If the repository classifies this identity as protected, STOP.

PN-3 Unattributed-loss snapshot.
The snapshot holds multi-company S3 exposure (candidate lots, remainders,
net costs). Planner assessment:
- the recognizing Admin sees only the physical result and the pending
  status;
- the Owner sees all companies' exposure;
- an ADM+ user recording an evidence-identified resolution sees the
  physical lot/serial identification only;
- each company's own exposure is visible to users entitled to that
  company's S3.

PN-4 Duplicate-evidence warnings as an oracle.
Warnings must not reveal the existence, company or content of evidence
the actor cannot see.

Planner option:
- show a detailed warning only within the actor's visible scope;
- route cross-scope matches to the Owner review queue;
- give the actor, at most, a non-identifying notice.

PN-5 Consuming project's allocated cost.
Approved baseline (WF-INV-07 and BR-ACC-02):
- the allocated cost is visible as the consuming project's own cost to
  users entitled to the consuming company's S3;
- the source company's purchases, suppliers, prices and other lots stay
  hidden;
- no source-company grant is implied.

WORKFLOWS §14 lists "further masking" as deferred, not an open business
choice.

Planner assessment:
- implement the baseline exactly;
- Level-1 further masking may remove only source-side identifiers not
  needed to present the consuming project's cost correctly.

Hiding the consuming project's own allocated cost from an entitled user,
or exposing any additional source-company S3, changes permitted
visibility → STOP.

A per-unit cost being arithmetically derivable from the consuming
project's own HPP is a consequence of the approved baseline. Do not
reopen it without evidence of an internal contradiction.

PN-6 Reset and onboarding channel (DEP-08).
Do not assume SMTP or buy a service.

Planner option:
- The Owner initiates onboarding and reset.
- Each issues a single-use, short-lived, hashed token or link.
- The Owner delivers it out of band.
- The password is set on first use.
- Every step is audited as a security event.
- Self-service email reset exists only as an optional path, conditional
  on P9 confirming a zero-cost channel.

If a secure reset flow cannot be delivered without a paid service, or
without materially changing the responsibilities in WF-ACC-01, STOP.

PN-7 Audit timelines and QS-14.
- Project audit before/after values by sensitivity.
- Cross-company events (for example allocation) must not leak the other
  side's S3.
- Only the Owner can open the Owner review queue.

PN-8 DIR-027 evidence exception.
Define server-verifiable conditions for "fully identified by definitive
evidence", for example:
- cited evidence of role-bound types (L-45, C-58);
- exact lot/serial and quantity identification;
- no discretionary choice of company.

Route every such resolution to QS-14.

If the approved meaning cannot be made server-verifiable without
inventing policy, STOP.

PN-9 Jobs, exports, caches, alerts, revocation.
- Authorize at the time of request.
- Jobs carry actor and company context and re-check current
  authorization before producing or delivering output.
- Cache keys include scope.
- Alerts are scope-filtered.
- Revocation takes effect on the next request and the next job step.

PN-10 Inertia.
- Shared props, partial reloads, lazy/deferred props and validation error
  bags pass the same policies and projection.
- Prop resources only, never raw models.

PN-11 Sessions.
Deactivation or revocation ending sessions (WF-ACC-02) requires either a
server-side session store or a session-version check. Choose one at
Level 1 and hand the infrastructure to P9. Valkey/Redis is acceptable for
sessions; it is never a system of record.

14. SELF-REVIEW AND INDEPENDENT ADVERSARIAL REVIEW
==================================================

Self-review:
- completeness against sections 7 and 8;
- anti-duplication;
- authority classification;
- traceability.

Independent adversarial review:
- Use a fresh read-only reviewer that did not write the documents (a
  subagent if available), given only the repository.
- Red-team at minimum the scenarios below.

Company-A-only Admin attempting to reach Company B through:
- direct URL or public_id;
- nested or related resources;
- shared masters (supplier price history, client relationships);
- pooled stock view → lot → cost;
- search;
- export;
- report filters;
- dashboards and queues;
- Inertia partial reload;
- issued PDF, evidence or import-file download;
- audit timeline;
- alerts;
- the duplicate-evidence oracle;
- the unattributed-loss snapshot;
- inter-company allocation views;
- cached aggregates.

Other attack scenarios:
- A revoked grant or deactivated user with an open session or a queued
  export.
- Admin attempting any of the following through any endpoint:
  - Force Complete;
  - write-off or its supersession;
  - found-stock attribution;
  - required-item relaxation;
  - unattributed-loss resolution without definitive evidence;
  - self-granting capabilities or companies;
  - demoting the last Owner.
- ADM without ADM+ performing corrections.
- ADM+ inter-company allocation leaking source-company data.
- Mass assignment of company_id, authority or state fields.
- Reset abuse:
  - user enumeration;
  - token replay;
  - token leakage in logs or the Referer header.
- Session fixation.
- CSRF on state changes.
- Stored XSS rendered into React or PDF.
- SVG or polyglot uploads.
- Path traversal.
- SSRF through the renderer.
- CSV formula injection.
- Brute force and throttling bypass.
- Backdating used to evade audit.

Classify every finding as exactly one of:
- CRITICAL
- HIGH
- MEDIUM
- LOW
- LEVEL-1 CORRECTION
- OWNER_DECISION_REQUIRED
- DEFERRED OBLIGATION (with its owning phase)
- NO DEFECT

Fix every valid finding. Re-test the scenarios after the fixes.

   isolation finding, and the disagreement cannot be reconciled with

c) P5 required approved-document amendments beyond narrow technical

19. CHECKPOINT COMMIT
==================================================

1. Review the complete diff: `git diff --ignore-cr-at-eol` plus all new
   files.
2. Stage explicit paths only, with CRLF normalization, for example:
   `git -c core.autocrlf=input add -- <paths>`
   Never use `git add -A` or `git add .`.
3. Verify the staged content:
   - `git diff --cached --stat` and `git diff --cached --check`;
   - the staged file list equals the intended census;
   - secret scan of the staged diff;
   - staged source-record blobs match their recorded hashes;
   - no unrelated, binary or temp files;
   - no .env or key material.
4. Commit once, message exactly:
   docs: finalize P5 security and authorization
5. Identity and attribution:
   - use only the Owner's existing configured Git identity;
   - do not modify git config;
   - do not pass --author;
   - no trailers of any kind;
   - never add Co-Authored-By, Generated-By or Assisted-By;
   - never name Claude, Anthropic, Fable, Opus or any AI/model/tool.
   If no identity is configured: STOP.
6. After the commit:
   - inspect the raw message (`git cat-file -p HEAD`) and confirm there is
     no attribution trailer;
   - confirm author and committer equal the configured identity;
   - confirm the tree and index are clean (CRLF-aware).

If automated review blocks staging or the commit:
- do not bypass it or retry variants;
- preserve the work;
- report the exact command and reason;
- STOP.

20. PUSH
==================================================

Immediately before pushing, run `git ls-remote origin refs/heads/main`.

It must equal the literal handoff SHA, the new commit must be its normal
descendant, and there must be no divergence. If so, run:

git push origin main

A normal push only. Never use:
- --force
- --force-with-lease
- reset or rebase of published history
- history rewriting
- remote deletion

On divergence: STOP and report.

If no working GitHub credentials exist:
- do not seek GUI or computer control;
- report the local commit SHA;
- instruct the Owner to run `git push origin main`.

Never claim publication until live origin/main confirms it.
