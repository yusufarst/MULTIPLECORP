==================================================

A major purpose of MultipleCorp is to eliminate repeated manual document work

For SYSTEM-GENERATED documents, the UX direction must support this pattern:

existing business data
        ->
prefilled draft
        ->
review / editable allowed inputs
        ->
document preview
        ->
validation
        ->
explicit finalization / issue.

The Admin must be able to see the document before it is finalized.

For desktop, when suitable, design a document-composer pattern such as:

LEFT:
- editable/confirmable data;
- fields that genuinely still need Admin input;
- validation;
- source-data context.

RIGHT:
- live document preview;
- approximately 40–45% of the workspace;
- page/zoom/full-preview controls where useful;
- preview remains visible while reviewing where practical.

Changes to allowed draft inputs should be reflected in the preview.

Important:

- do not make the final PDF itself the editable source of truth;
- reused Company/Client/Project/Item/Delivery/Finance data should come from
  the approved business records;
- if such data is wrong, correction should happen through the authorized
  source/input flow;
- clearly distinguish carried-forward data from data the Admin must enter;
- a draft preview does not satisfy issuance;
- final/issued documents retain approved immutability, revision and void
  semantics;
- external uploads remain distinct from generated documents.

For mobile, do not force a desktop split layout.

A mobile flow may use:

Edit
  ->
Preview
  ->
Finalize

or an appropriate full-screen preview.

First verify this requirement against P0–P6 document semantics.

If any requested behaviour would require changing approved document/business
semantics, surface that exact conflict rather than inventing behaviour.
