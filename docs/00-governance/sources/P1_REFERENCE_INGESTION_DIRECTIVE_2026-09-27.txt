==================================================
GOLDEN OPERATIONAL FLOW
==================================================

Treat the attached flow diagram as an important reference for the
normal operational path.

Conceptually validate the sequence:

LOGIN
→ AUTHENTICATION
→ COMPANY SCOPE / PERMISSION
→ DASHBOARD
→ CREATE OR OPEN PROJECT
→ SELECT COMPANY
→ SELECT CLIENT
→ SELECT UNIT / PIC
→ SELECT CHANNEL
→ PRODUCTS / SERVICES
→ PRICING / TAX / VALUE
→ QUOTATION
→ REVISION IF REQUIRED
→ APPROVAL
→ STOCK / PROCUREMENT DECISION
→ PURCHASE IF REQUIRED
→ OPTIONAL PO
→ WAREHOUSE OR DROP-SHIP
→ RECEIVING / BARCODE / SERIAL WHEN APPLICABLE
→ DELIVERY
→ PARTIAL OR FULL DELIVERY
→ DELIVERY DOCUMENTS
→ TRANSACTION DOCUMENTS
→ INVOICE
→ ADMINISTRATIVE DOCUMENTS / SPJ
→ BILLING
→ RECEIVABLE
→ PAYMENT
→ PARTIAL PAYMENT LOOP WHEN REQUIRED
→ COMPLETION VALIDATION
→ PROJECT COMPLETED
→ DASHBOARD / REPORTS UPDATED

This is the GOLDEN NORMAL FLOW.

However:
do not force every project through irrelevant steps.

Examples:

- service-only project may not require warehouse movement
- drop-ship should not fake warehouse receiving
- PO is optional
- required administrative documents vary by client
- SIPLAH is a transaction channel
- partial delivery/payment creates controlled loops
- correction flows must preserve history

Model optionality explicitly rather than creating fake transactions.

==================================================
PROJECT COMPLETION GATE
==================================================

Use the attachment as a reference for the rule that a project is not
"Completed" merely because goods were delivered.

Planning must define a reliable completion gate.

At minimum evaluate:

- required fulfillment completed
- deliveries completed or formally closed
- required documents issued
- required administrative documents complete or validly waived
- billing completed when applicable
- receivable resolved or formally handled
- no unresolved stock correction
- no unresolved payment correction
- required audit history exists

Refine this during domain/workflow planning if a better implementation
preserves Owner intent.

==================================================
DEFINITION OF DONE
==================================================

Preserve the core principle from the PDF:

A feature is NOT DONE merely because the UI works.

Every Build Unit must explicitly evaluate where applicable:

1. Business correctness
2. UI/UX correctness
3. Backend behavior
4. Database integrity
5. Security / Authorization
6. Concurrency / Idempotency / Integrity
7. Performance / N+1
8. Automated verification

The executor must not mark work complete with statements such as:

"feature implemented"
"looks good"
"works on screen"

without deterministic verification.
