2. OWNER DECISIONS ON THE REVIEW FINDINGS
==================================================

The verbatim source text is Appendix A. My agreement in it refers to the
planning recommendations stated here.

R-01 (A) — Account-wide limit on second-factor guessing.

  Scope
  - One failed-code count per account, shared across all IP addresses and
    across every authentication or recovery step that accepts a TOTP code or
    a recovery code:
      * the sign-in challenge after a password or a Google sign-in;
      * recovery-code sign-in (path b);
      * the current-code check of device replacement;
      * viewing and regenerating recovery codes;
      * disabling TOTP;
      * Google linking;
      * every other step that authenticates with a TOTP or recovery code.
  - Enrolment confirmation, which checks a code against a secret just shown
    in the same session, stays under the existing throttles only.

  Threshold
  - The fifth failed code within the attempt window immediately does both:
      * it invalidates the current challenge, or the pending step of the
        other code-accepting flow;
      * it starts the account-wide second-factor cooldown across all IP
        addresses.
  - The attempt window is a project-defined rolling period (Level 1).

  Cooldown
  - While the cooldown runs, every code-accepting step for the account is
    refused without evaluating the submitted code, so a refused recovery
    code is neither checked nor consumed. Each refusal is recorded.
  - Every later threshold breach lengthens the cooldown along a
    project-defined progression, capped at 15 minutes.
  - The progression below the cap is a Level-1 choice. It is stated
    identically wherever the limit is described, and it is a P8 test
    obligation.
  - The cooldown always ends. It is never a permanent account lockout.

  Evidence and counters
  - A successful, legitimate second-factor authentication never deletes or
    rewrites security events.
  - It never silently resets the escalation level or the aggregated counts
    that feed abuse detection and the Owner alert.
  - Level-1 rule, stated identically and tested in P8: how the window count,
    the escalation level and the aggregation decay over time, and what — if
    anything — a success resets.
  - Any reset caused by a success is itself recorded as a security event.

  Recovery codes
  - Recovery codes keep their transactional single-use consumption under the
    account row lock (section 7.4). This limit adds to that protection and
    never replaces it.

  Alerting
  - Each threshold breach raises an alert to the Owner (LG-07). Failure
    events are aggregated for alerting.

  Defense in depth
  - The existing per-account+IP and per-IP throttles stay.
  - If the limiter store is unavailable, code-accepting steps fail closed,
    as section 7.4 states.
  - This supersedes "throttled like login" of section 7.4 for the
    second-factor step.

R-02 (A) — The key-and-database-leak command becomes a full incident
response for every account:
  - every TOTP secret and recovery-code set destroyed;
  - every password made unusable;
  - every unused credential token revoked;
  - every session deleted;
  - the HMAC keys rotated;
  - the leaked key retired from the previous-keys list as soon as every
    ciphertext that must survive has been re-encrypted under the new key
    (TOTP data is voided, not re-encrypted);
  - Google links kept, not eligible until TOTP is active again (K2);
  - one audit event and one security event per affected account, with the
    operator's identity recorded as AU-14 records it.
  Recovery uses existing paths only: AU-14 operator recovery for each Owner
  account, then Owner-issued RESET links for every other account. The
  command is operator-run, never run by an agent. This supersedes the
  voiding command of section 7.6.

R-05 — When a grant or a role assignment makes an account high-risk and the
account has no confirmed TOTP, the same command makes its password unusable,
revokes its unused credential tokens, ends its sessions and issues one RESET
link for out-of-band delivery (AU-12). An account that already has confirmed
TOTP keeps its password; its sessions end as section 7.3 states. The first
enrolment of any high-risk account raises an alert to the Owner. The reset
command under `users.manage` also works for an account without TOTP
(password reissue and unlink).

R-06 (yes) — Viewing recovery codes requires password confirmation and a
current TOTP code. Viewing and using recovery codes raise alerts for every
high-risk account.

R-07 — If the breached-password range service fails or does not answer
within a short project-set timeout, the password is accepted only when it
passes the local list and every other rule of section 7.2; a security event
records that the remote check was skipped. The check never runs inside a
database transaction. No offline corpus is required. This replaces the
fail-closed behaviour in the current drafts.

Accepted residual risks, added to the four of K4:
  (e) a person who holds an account's password can deliberately delay that
      account's sign-in by triggering the account-wide cooldown of R-01;
  (f) while the range service is unreachable, a breached password that
      passes the local list can be set.
