7. THE APPROVED DESIGN
==================================================

7.1 Libraries (one-time decision, AICWDF §4A.1)
Laravel-native authentication: Fortify for the login pipeline, two-factor,
password confirmation and password update; Socialite for Google.
Fortify policy: registration OFF; password reset OFF (the project's
credential-token store stays, AU-11/AU-12); e-mail verification OFF;
profile update OFF; passkeys OFF; password update ON with a project action
enforcing 7.2 and ending other sessions; two-factor ON with confirmation,
password confirmation and an explicit window; password confirmation ON at
15 minutes; "remember me" never used; login and two-factor limiters defined
by the project per AU-05.

7.2 Password (replaces the rule of AU-03)
8 to 128 characters; at least one lowercase letter, one uppercase letter,
one digit and one symbol; NFC normalization; paste and password managers
allowed; no periodic expiry; a change is forced only on evidence of
compromise. Rejected when: the `uncompromised` check finds it; or it is in a
locally bundled list of common passwords, checked first and independent of
any network call (list and licence chosen at implementation under DEP-07);
or it contains the account's name or e-mail, the product name or a company
name. The remote check runs outside any database transaction; its failure
behaviour is stated. This is an Owner-selected profile, not a NIST claim.
Password hashing (AU-02) is unchanged.

7.3 High-risk accounts and mandatory TOTP (K1)
- The definition of K1, evaluated on effective capabilities.
- By RG-02 every OWNER_ONLY capability takes effect only through the OWNER
  role, so all account, permission, company, bank-account, identity-asset,
  credential-link and import-commit authority is covered by criterion (1).
- Owner recovery (AU-14) is an operator console mechanism, not a capability,
  and does not change the definition.
- When a grant makes an account high-risk, the granting command ends that
  account's sessions in the same transaction; the next login forces
  enrolment. Every request also checks that a high-risk account's session
  was established with TOTP.
- A high-risk account without TOTP can, after its password is accepted,
  reach only the enrolment page.

7.4 TOTP
Six digits, 30-second period, one step of tolerance — period and window set
explicitly by the project. Secret encrypted with the application key. Code
reuse rejected through a durable per-account last-accepted time step with a
conditional update. Attempts throttled like login, never lockout, limiter
fails closed. QR code generated locally. Active only after one correct
code. No "remember this device". The pending login challenge is bound to the
account's current factor state and expires; the session ID is regenerated
when the challenge succeeds. A mandatory account cannot disable TOTP, only
replace the device.
Recovery codes: Fortify-native, encrypted at rest, viewable again only after
password confirmation, regenerated only with password and a current code,
each usable once, consumed under the account row lock in one transaction.

7.5 Reset and recovery contract (K3)
In every path: pending login challenges are void; the password confirmation
of the current session is cleared; other sessions are ended; the account's
unused credential tokens are revoked; an audit event and a security event
are written; the account is told at its next login; Owner-account events
and Owner resets raise alerts (LG-07). A credential link never creates a
session and never bypasses TOTP; only an OWNER_RECOVERY link resets TOTP.

 a. Normal device replacement — needs an active session, password
    confirmation and a current code. The old secret and codes stay valid
    until the new device is confirmed, then are destroyed; new codes are
    issued at confirmation; this session continues with a new ID; Google
    eligibility and the password are unchanged.
 b. Device lost, recovery code available — password plus one recovery code,
    consumed at once. The session can only enrol a new device. At
    confirmation the old secret and remaining codes are destroyed and new
    codes issued. Google sign-in is not eligible until confirmation; the
    link is kept.
 c. Owner resets an Admin's TOTP — `users.manage`, step-up, mandatory
    reason. Secret and codes destroyed at once; all sessions of the account
    ended; the password is made unusable and one new RESET credential link
    is issued for out-of-band delivery; the Google link is unlinked with
    reason CREDENTIAL_REISSUE and the acting Owner as `unlinked_by`. The
    person sets a new password, logs in and must enrol.
 d. Owner lost device and codes, another Owner exists — path c, performed by
    the other Owner, with an alert to the affected Owner.
 e. Operator recovery (AU-14 extended) — the audited console command issues
    an OWNER_RECOVERY link only for an OWNER-role account; issuing changes
    nothing else. Using the link sets a new password, destroys the TOTP
    secret and codes, ends all sessions and unlinks Google. That unlink
    happens in the unauthenticated credential flow, so no application
    account performs it: `unlinked_by` is NULL and the reason is
    OWNER_RECOVERY. The operator has no application-user representation and
    none is created. The operator's identity stays where AU-14 already puts
    it — the audit event and the security event of the link's issue — and
    the audit event of the link's use refers to that credential link, so the
    chain from the unlink to the operator is preserved. The Owner then logs
    in and must enrol. The command never sets or reads a secret. Agents
    never run it (SX-04).
 f. A non-mandatory account disables TOTP — allowed only while the account
    is not high-risk, with password and a current code. Secret and codes
    destroyed; this session continues with a new ID; the Google link is
    unlinked with reason TOTP_DISABLED and the account itself as
    `unlinked_by`. A later high-risk grant ends its sessions and forces
    enrolment.

7.6 Key management
The key is the application key, held by the P9 operator in environment
configuration outside the repository, the web root and the database; a
database backup holds ciphertext only. Rotation uses the framework's
previous-keys list, so existing secrets stay readable while the old key is
listed. The project adds: a dated key register kept in the operator's
secret store; an operator command that re-encrypts all TOTP secrets and
recovery codes with the current key, after which, and only after a verified
count, the old key may be retired; an operator command that voids every
TOTP enrolment when the key is believed leaked together with the database.
That command does not unlink any Google identity: the links stay and Google
sign-in is simply not eligible until each account enrols again (K2). It is
audited like AU-14, with the operator's identity in the audit event.
Loss of the key makes secrets unreadable but recovery does not need them:
operator recovery for the Owner, then Owner resets for others. P9 owes key
storage and permissions, the rotation and re-encryption runbook, pairing
each backup with the key valid at that time, and a recovery test.

7.7 Google sign-in (K2)
- Authorization code flow through Socialite; scopes `openid email`; always
  `prompt=select_account`; no One Tap, no Google script on any page; no
  Google token stored; no Google API used.
- `state` through Socialite, plus a project attempt marker in the session
  carrying a maximum age and the purpose (sign-in or linking); PKCE enabled;
  a project `nonce` generated, kept in the session and checked against the
  ID token; the ID from Socialite confirmed to be `sub`.
- A second callback while a TOTP challenge is already pending leads to that
  challenge and does not disturb it. A stale or mismatched callback gets the
  generic failure.
- Mapping only through `sub` in `user_external_identities`. No automatic
  linking by e-mail, no auto-registration. Every failure gives one generic
  message that reveals nothing about accounts.
- Every account keeps a password (fallback, step-up, linking).
- Linking: by the account holder, inside an active session, with password
  confirmation and a current TOTP code; one Google identity per account and
  one account per Google identity; the same pair linked again is a no-op; a
  `sub` already linked elsewhere is refused with a security event and an
  Owner alert.
- A Google identity never grants a role, capability or company scope.

7.8 Google identity lifecycle
Stored: provider, `sub`, the e-mail at link time (display only, never a
key, not updated), link and unlink facts. Because no token is stored, the
application does not detect Google-side changes.
- Google e-mail changes: no effect.
- Consent revoked at Google, or Google account deleted: felt only at the
  next Google sign-in attempt; existing MULTIPLECORP sessions continue until
  their own limits.
- Google sign-in fails: generic message, security event, password login
  remains.
- MULTIPLECORP account deactivated: the link is unlinked inside the
  deactivation transaction.
- Unlink by the user: password confirmation; other sessions ended.
- Unlink by the Owner: `users.manage`, step-up, reason; all sessions of the
  account ended.
- Unlink through reset or recovery: paths c, d, e and f of 7.5.
- Revoking sessions is a separate action and does not change the link.

7.9 Storage
- `users` gains four fields: `two_factor_secret`, `two_factor_recovery_codes`,
  `two_factor_confirmed_at` (framework) and `two_factor_last_step`
  (project); all nullable; cleared together on reset or disable; a
  constraint that confirmation requires a secret.
- New IAM logical table `user_external_identities`:
  * `user_id` — foreign key to `users`, RESTRICT, required.
  * `provider` — constrained to `google`.
  * `provider_subject` — required.
  * `email_at_link` — nullable, display only.
  * `linked_at` — required.
  * `linked_by` — foreign key to `users`, RESTRICT, required. Meaning: the
    authenticated application account that created the link. In V1 only the
    account holder links, so `linked_by` equals `user_id`, enforced by a
    constraint.
  * `unlinked_at` — nullable.
  * `unlinked_by` — foreign key to `users`, RESTRICT, nullable. Meaning: the
    authenticated application account whose action performed the unlink. It
    is never an operator, a system identity or a placeholder user.
  * `unlink_reason` — constrained to SELF, OWNER, DEACTIVATION,
    CREDENTIAL_REISSUE, TOTP_DISABLED, OWNER_RECOVERY.
  * Unlink contract, one row per path:
      SELF               account holder unlinks        unlinked_by = user_id
      OWNER              Owner via `users.manage`      unlinked_by = that Owner
      DEACTIVATION       account deactivated           unlinked_by = the Owner
                                                       running the command
      CREDENTIAL_REISSUE Owner resets TOTP (7.5 c, d)  unlinked_by = that Owner
      TOTP_DISABLED      holder disables TOTP (7.5 f)  unlinked_by = user_id
      OWNER_RECOVERY     OWNER_RECOVERY link used      unlinked_by = NULL
                         (7.5 e)
  * Constraints: while a row is linked, `unlinked_at`, `unlinked_by` and
    `unlink_reason` are all NULL; once unlinked, `unlinked_at` and
    `unlink_reason` are both present, and `unlinked_by` is NULL exactly when
    the reason is OWNER_RECOVERY.
  * Partial unique keys on (provider, provider_subject) and on (user_id,
    provider) for rows not unlinked; an index on `user_id`.
  * Rows are never deleted; relinking adds a row. The row is the history;
    every link and unlink also writes an audit event in the same transaction
    and a security event.
- IAM becomes 8 tables and the logical total 125. Sessions, the
  credential-token store, pending challenges, OAuth state and limiter
  counters stay infrastructure or runtime and outside the count.
- No other field and no other table. Making a password unusable stores an
  unguessable random hash.

7.10 External dependencies (zero recurring cost)
Google OAuth client (my Google Cloud access; P9 sets it up per environment);
the breached-password range service used by `uncompromised`; authenticator
apps on users' own phones.
