## 14. Numbering concurrency

| ID | Rule |
| --- | --- |
| NM-01 | The counter row is the last lock of any action (LK-31), so it is held only for the statements that remain before commit; every business anchor, the project row included, is locked before it. |
| NM-02 | **Allocation.** Where NM-03 allows a first use, insert-or-lock the counter (FU-07) with `next_value` 1; then one statement increments the counter and returns the pre-increment value. Exactly one row must be affected. The row lock serializes issuers until commit. |
| NM-03 | **Period and seeds.** `period_key` comes from the version's `business_date` and the numbering scheme effective on that date, and is stored with the number; a YEAR key and a MONTH key never coincide. The allocator **fails closed**: an issue never creates a counter for a company and sequence type that has no seed boundary, and a numbering scheme creates no counter by itself. Every counter that is not created on first use is a **seed** that states its first number: the first number after every number of its period issued outside this database, whatever date that number carries, or 1 where there is none. Seeds come from the migration — AX-28 writes them from the import rows it names (DATABASE §24; HO-32) — and from the Owner's numbering command (NX-01), whose seeds carry the Owner's number and no import row; a counter created on first use carries no seed value. A granularity **governs** a period when a scheme of the type with that granularity is in force on some date of the period. An import seeds only periods whose dates all lie on or before its cutoff and, while the type has no seed boundary later than that cutoff, the periods into which the cutoff date falls under every granularity that governs them; AX-28 applies this rule again when it commits a seed row, and records a row the rule no longer admits as SKIPPED, with no counter and no refusal. For a company or a type that no import seeds, the numbering command writes the **start** of numbering: a seed for the period into which the day it is recorded falls, under every granularity that governs it; the start is refused before go-live, once the type has a seed boundary, and while a batch that is not ABORTED holds a VALID seed row of the type. The **seed boundary** of a company and type is a date: the latest of the cutoff dates of the batches, whatever their state, that hold a COMMITTED seed row of the type and the day of the start, which the start's own audit event records apart from its counters (DATABASE §23; HO-27) — so a counter lost by a defect cannot move it, and no other seed of the numbering command counts. It reads only typed columns, never `jsonb` (DATABASE §17) and never the counters: a seed row carries a registered `import_kind` for its sequence type, and the start's audit event carries the company and a registered action code for the start of its sequence type, as SQ-23 registers the routed variants of an action. It rests on what the migration and the Owner vouch for: once the type issues here, no number of it has been issued outside this database after its boundary, none carries a date after it, and each belongs to a period that contains its date or the day it was issued (HO-32; HO-39). **Go-live** is the day this database became the system of record, recorded once at the cutover (HO-32); until it is recorded, nothing is created on demand and the numbering command neither starts nor seeds. A period is **live** when it begins after the seed boundary — whatever its granularity and whichever scheme was in force on the dates it covers — and does not lie wholly before go-live. A counter is created on first use only for a live period; a period that is not live gets a counter only from a seed. Once the type has its boundary, the numbering command also seeds, with the first number the Owner states, any period of the type that has no counter and is not live — never one that lies wholly before go-live, which only the migration seeds (DATABASE §10), nor one for which a batch that is not ABORTED holds a VALID seed row. The numbering command — start, seeds and scheme changes — locks its company row (LK-06) and reads schemes, counters and batch rows under it; so does the Owner's commit request of a batch (NX-13), which is refused unless the batch holds a seed row for each period into which its cutoff falls under every granularity that governs it, unless the type's seed boundary is later than the cutoff. A seed that creates its counter first proves that no version issued here, live project or tombstone carries a number of its period at or above its first number, and an issue that finds no counter for a period that is not live first proves that none of them carries that period; a failed proof means a lost counter (SQ-18). Otherwise an issue that may create no counter is REJECTED (C-10) and never restarts at 1 over numbers issued outside this database, which are no rows here and which no UNIQUE key could notice: a document backdated into an unseeded pre-cutover period — a month inside a seeded year included — is REJECTED, and one backdated to before the start is REJECTED until its period is seeded. Once a type has its boundary, the numbering command refuses a scheme it adds or changes that takes effect before the day it is recorded, unless the scheme only extends the type's schemes backwards over dates no scheme of the type covered; it refuses a scheme whose first period is not live and has no counter, unless the same command seeds that period or the scheme is such an extension; and while a batch that is not ABORTED holds VALID seed rows of the type, it refuses a scheme that would govern the period into which that batch's cutoff falls while the batch holds no seed row for it. A change of granularity therefore starts a live period or continues a counter that exists or is being seeded, and a backward extension is admitted without a seed, its periods that are not live and have no counter REJECTED until they are seeded. This narrows DATABASE §10, which allows a counter on demand for every period from go-live on: no counter exists before the type has its seed boundary, and a period that is not live gets a counter only from a seed, never on demand. A seed that meets an existing counter may raise it, never lower it, and moves its seed value with it; it raises a defect alert when the counter has drawn a number and the new seed exceeds the counter's first number — its seed value, or 1 after a first use — because only then can a number have been reused; any other raise, the delta of HO-32 among them, is an ordinary, audited effect. For the verification of DATABASE §3.1, a counter's seed value is its migration seed, whoever wrote it. |
| NM-04 | A rolled-back issue consumes nothing: the increment is part of the transaction. A committed number is never reused: counters are never lowered, a void keeps its version row and a discarded project keeps its tombstone. |
| NM-05 | A backdated issue draws the next number of its own business-date period; chronology and number order may differ (DIR-018). |
| NM-06 | A double issue of one draft is one effect (BD-06). |
| NM-07 | **Committed values are reused, never recomputed.** Renders, retries, replays and sweeps read `business_date`, `period_key`, `sequence_no`, `revision_suffix` and `formatted_number` from the ISSUED version row (GAP-016). A BASE_SUFFIX revision takes its predecessor's suffix plus one under LK-30 and draws no counter; a NEW_NUMBER revision draws from the period of its own business date. |
| NM-08 | Project numbers use the same allocator with sequence type PROJECT at project creation. Discarding a DRAFT project writes its `retired_numbers` tombstone in the discarding transaction (L-37); the number stays consumed. |
| NM-09 | **Backstops:** UNIQUE (company, type, period, sequence number, revision suffix) and UNIQUE (company, type, formatted number) on versions, and the two UNIQUE keys of `retired_numbers`; a violation is SQ-19, because the allocator must never produce one. |
| NM-10 | Never `MAX(number) + 1`, never a PostgreSQL sequence for a business number, and no gapless promise: numbers are unique, monotonic per counter, append-only and never reused (C-10; BR-DOC-02). |

```text
NON-EXECUTABLE ILLUSTRATION — allocation at LK-31 (placeholders :c, :t, :p)

INSERT INTO number_sequences (company_id, sequence_type, period_key, next_value, seed_value)
VALUES (:c, :t, :p, 1, NULL)
ON CONFLICT (company_id, sequence_type, period_key) DO NOTHING;   -- only where NM-03 allows a first use; a seed states its value instead

UPDATE number_sequences
   SET next_value = next_value + 1
 WHERE company_id = :c AND sequence_type = :t AND period_key = :p
RETURNING next_value - 1 AS allocated;                            -- exactly one row, else NM-03 or a failure
```

## 15. Jobs, scheduler and queue

One main queue (OB §35). Durable database rows are the record of work owed; the queue, cache and limiter store (Valkey) is never a system of record. ARCHITECTURE §11 names the six jobs with a business-visible trigger and notes that a job performing business effects invokes actions with deterministic command identities; this register fixes the mechanics of those six and adds the three operational tasks the mechanisms need (JB-07–JB-09).

- **After-commit dispatch.** Every job is dispatched by the framework's after-commit mechanism from phase F; a job dispatched inside a transaction that rolls back is discarded. The payload is built at dispatch and carries identifiers only — job type, payload format version, the durable row's id, the actor and company context, the correlation id — never S3 values or secrets, and nothing sensitive is placed in the propagated log context (DP-09).
- **Scheduler.** One cron entry runs the scheduler each minute; every scheduled task uses overlap protection with an explicit expiry longer than its longest run. When the store is down a task cannot take its lock and does not run; the next minute tries again. A daily task that misses its minute that way is not caught up by the scheduler: P9 alerts on a day without a successful run (HO-25).
- **Store unavailable or emptied (GAP-013).** A committed action stays committed (SQ-21). The durable row — a rendition attempt, an export request, an import batch with its commit request — holds the work, and the sweeps (JB-02, JB-09) re-dispatch it when the queue returns, also after the store lost its contents: nothing on it is needed for correctness (PERFORMANCE SZ-09). Limiters follow H6-07. Sessions and every business fact live in PostgreSQL and are unaffected. Worker restarts on deployment use the cache and therefore need the store; P9 monitors it (HO-24).
- **Payload versioning (GAP-012).** Every payload carries a format version. A worker that meets a newer version than it knows releases the job back with a delay instead of failing it; a newer worker accepts the previous version for one release. Deterministic command identities make re-execution by either version safe. P10 sequences expand-only migrations, deployment and worker restart (HO-31).

## 16. Authorization and revocation races

| ID | Rule |
| --- | --- |
| RV-01 | **In-command re-authorization (H6-01).** Every command locks its actor's `users` row at LK-03 — after the project rows, before every other anchor — and, in statements issued after that lock is granted, re-reads the account's active flag, role, capability grants and company grants and re-checks scope, capability and prerequisites (AZ-05). It runs before any precondition is read, so a denial answers as AZ-11 and discloses nothing. The grant or allocation authority that AZ-08 and XL-1 require for an effect the actor chooses on another company's record is checked next, from the same re-read; failing it is not a denial but the REJECTED-and-routed outcome of SQ-23. |
| RV-02 | **Access changes.** A command that changes an account's role, capability grants, company grants or active state locks that account's row at LK-03 as well (TX-09). The lock is the same exclusive one a command of that account takes, so the change waits for the account's command in flight, and every later command of the account waits for the change and then reads the new state. Both queue on the row, so a stream of commands cannot keep the change waiting (D-CC-02). |
| RV-03 | **Linearization point:** the commit of the access-changing command. A command that held the account's row first ends before the change commits and was authorized when it ran; a command that arrives later waits and is then denied — "rejected on its next request" (AZ-03). A read request evaluates the committed grants once, at its start. |
| RV-04 | **Last active Owner (H6-02).** A command that would deactivate, or change the role of, an account holding the OWNER role locks the OWNER role row (LK-02) first, then the user rows, and counts the active Owners that would remain; zero is REJECTED (RG-09). Two such commands are serialized by LK-02. |
| RV-05 | **Deactivation (RG-10; H6-06)** is one transaction: the target's row locked, its grants revoked, its unused credential tokens revoked, its `sessions` rows deleted by `user_id`, its export requests withheld (RV-08) and its active Google link unlinked with reason DEACTIVATION and `unlinked_by` = the Owner running the command — a conditional update of the unlink columns of a row its LK-03 anchors — with that unlink's audit event in the transaction and GOOGLE_UNLINKED after it (SECURITY AU-24). A request of that account arriving afterwards finds no session. A login that was being verified while the deactivation committed may still write a session row afterwards: the per-request check refuses it and deletes it (AU-09), and a reactivation deletes the account's sessions again in its own transaction, so no such row can come back to life. The per-request active check costs nothing extra: `is_active` is a column of the user row the session guard already loads. |
| RV-06 | **Idle timeout (AU-07; H7-13).** A background request — polling, deferred and visibility-triggered props, prefetch, thumbnails and previews — reads the session but never writes it, so the session row's last activity is the last user-initiated request and the 60-minute idle limit is the session lifetime itself; the 12-hour absolute limit is checked against the login time kept in the session. The framework's session middleware writes on every request, so this needs a variant of it that skips the write (HO-20). Background is decided on the server: thumbnail and preview routes are background by their route, any other GET only when the client marks it, and a request that is not a GET never is — so a background request can run no command. A download the user starts is a user-initiated request and extends the session like any other. |
| RV-07 | **Jobs (H6-04).** A job step re-resolves its actor's scope and capabilities when it starts and before each unit of work that opens a transaction of its own; a revoked or deactivated actor ends the job with nothing delivered (DP-09). An export reads inside one snapshot, where a later revocation cannot be seen, so it is checked before the snapshot opens and again at delivery (RV-08). |
| RV-08 | **Export delivery (DP-07).** A command that revokes a company grant or a capability, changes a role or ends an account's active state marks as WITHHELD, in its own transaction, every export request of that account that is PENDING, RUNNING or READY and not yet expired and whose recorded company set, capability set or masking context the account's grants no longer cover; P9's cleanup removes a withheld file at once (HO-29), and a job whose READY update the mark defeats removes the file it wrote (JB-03). The download is an ordinary GET and changes no business state (WS-04): it serves a request only in state READY, and only after comparing the requester's current company scope, capabilities and masking context with the recorded ones — so a request that escaped the mark is refused all the same, with the AZ-11 answer — and it writes the security event LG-02 requires. |
| RV-09 | **Replay (H6-03).** A replay re-authorizes as RV-01 before anything recorded is returned (CI-05). |
| RV-10 | **Credential changes (AU-09; AU-11).** The session keeps a keyed digest of the password hash its login verified, and the session guard compares it on every request with the hash on the account row it already loads; a mismatch ends that session. A password set or change therefore ends every other session exactly — also one that a login verified against the old password was still creating. The change itself is one TX-07 transaction under the account's row lock: re-read `is_active` and the hash the request had verified — a difference answers the generic failure, so two changes verified against one old password cannot both apply — set the new hash, revoke the account's unused links and delete its other sessions; the changing request then regenerates its session identifier (AU-06) and stamps its own session with the digest of the new hash. Login verifies outside any transaction within a slot of H6-12 and writes nothing to the account row unless the stored hash is due for a rehash (AU-02): the rehash is one conditional update of TX-07 that matches only while the row still holds the hash that was verified, so it can never write a hash of an old password over a newer credential. The session is stamped with the digest of the hash the login verified or, when its rehash update changed the row, of the hash that update wrote — never of a hash read afterwards. A rehash update that matches no row answers the generic failure: the stored hash changed while the login was being verified — by a password change, or by the rehash of another login of the account — and the user logs in again. One that cannot get the row within its lock timeout is left for the next login. A rehash changes the stored hash without changing the credential, so it ends the account's other sessions once: at the account's first login after P9 changes the hashing parameters, which is a planned event (HO-26). The session also keeps whether it was established with TOTP and a keyed digest of the account's `two_factor_confirmed_at`; the same per-request comparison with the account row ends a session whose enrolment has changed — except the session that made the change, which is restamped in the same request — and ends the session of a high-risk account that was not established with TOTP unless it is an enrolment-only session (SECURITY AU-06, AU-18). Both comparisons read the account row and the role and grants the resolver loads for the request, so they add no query. |
| RV-11 | **A change that makes an account high-risk (SECURITY AU-18; H6-15).** An NX-02 command that assigns the OWNER role or grants an ADM_PLUS capability or `finance.view`, `cost.view`, `profit.view` or `evidence.view` evaluates the high-risk test on the target's role and grants as its change leaves them, read under the target's row (LK-03; RV-02); when the account becomes high-risk, the same transaction deletes all its `sessions` rows by `user_id` as its last statements (LK-05). A login verified while the change commits may still write a session row afterwards: the per-request check of RV-10 ends it at its first request unless that login passed the TOTP challenge. |
| RV-12 | **Accepting a TOTP code (SECURITY AU-16; H6-13).** The code's time step is found outside any transaction, against the decrypted secret — a few HMAC computations with the project's period and window, never a password hash — starting after the account's stored `two_factor_last_step`. Then one TX-07 transaction: lock the account's row (LK-03); re-read `is_active` and the TOTP fields and, at a challenge, compare the challenge's digest with the state just read — a difference voids the challenge with the generic answer; accept the code by one conditional update that matches only while the stored step is earlier than the code's (NON-EXECUTABLE: `UPDATE users SET two_factor_last_step = :step WHERE id = :id AND two_factor_last_step < :step`) — exactly one row, otherwise the generic answer, because another request accepted that step or a later one first; then the effects of the step that asked for the code — the session's establishment, a replacement, a disable, a regeneration, a link — with their audit and security events; commit; and only then regenerate the session identifier and stamp the session where SECURITY AU-06 says so. |
| RV-13 | **Consuming a recovery code (SECURITY AU-19, AU-20 b; H6-13).** After a correct password at the challenge, one TX-07 transaction: lock the account's row (LK-03); compare the challenge's digest; decrypt the stored set, find the submitted code by constant-time comparison and write the set without it, re-encrypted, by an update that matches only while the stored ciphertext is the one read under the lock — exactly one row; revoke the account's unused credential links (LK-04) and delete its other sessions (LK-05) as the last statements, with RECOVERY_CODE_USED's audit event; commit; then regenerate the session identifier and make the session enrolment-only (SECURITY AU-18). A second submission of the same code — concurrent or later — waits on LK-03, finds its challenge void or the code gone and gets the generic answer. |
| RV-14 | **Confirming a device and disabling TOTP (SECURITY AU-16, AU-20 a, b, f; H6-15).** A confirmation — of a first enrolment or of a replacement — checks the code against the new secret held in the session, as RV-12 finds a step; then one TX-07 transaction: lock the account's row (LK-03); re-read the TOTP fields and compare them with the state the enrolment started from — no enrolment for a first one, the same confirmed enrolment for a replacement, the account in recovery for path b — refusing on a difference; write the four TOTP fields in one statement — the encrypted secret, eight new encrypted recovery codes, the confirmation time and the confirming code's step (C-62); revoke the account's unused credential links (LK-04) and delete its other sessions (LK-05) last, with TOTP_ENROLLED's or TOTP_REPLACED's audit event; commit; then regenerate the session identifier, restamp the session and show the new codes once. A disable accepts a current code as RV-12 does, in the same transaction, after password confirmation: under LK-03 the high-risk test runs on the state read there and a high-risk account is refused; the four fields are cleared in one statement; the account's active Google row is unlinked with reason TOTP_DISABLED and `unlinked_by` = the account by a conditional update of its unlink columns; unused links are revoked and other sessions deleted last; the audit events of the disable and of the unlink are written; commit; the session identifier is regenerated and the session restamped. |
| RV-15 | **An Owner's TOTP reset or Google unlink of another account (SECURITY AU-20 c, d, AU-24; H6-15).** SF-CMD commands of NX-02 (TX-09) with step-up and a mandatory reason, whose target is never the actor. The unusable password hash is computed before the transaction (section 3). The command locks the acting Owner's and the target's rows at LK-03 in id order and re-authorizes (RV-01); a reset of a target without active TOTP, or an unlink of a target without an active link, is REJECTED with the current state. A reset clears the target's four TOTP fields and writes the unusable hash in one statement, unlinks its active Google row with reason CREDENTIAL_REISSUE and `unlinked_by` = the acting Owner, revokes its unused links and inserts one RESET link (LK-04) and deletes all its sessions (LK-05), the token and session statements last (LR-02); an unlink sets the active row's unlink columns with reason OWNER and `unlinked_by` = the acting Owner and deletes all the target's sessions. Each writes its audit events in the transaction, authority class OWNER_ONLY, and its security events after it (TOTP_RESET, GOOGLE_UNLINKED). The RESET link is shown once to the acting Owner, as SECURITY AU-12 requires. |
| RV-16 | **The Google link and the account's own unlink (SECURITY AU-23, AU-24; H6-14).** The callback's checks and Google's calls run before any transaction (SECURITY AU-22). The holder's confirming request then runs one TX-07 transaction: lock the account's row (LK-03); check the password confirmation and accept the current code (RV-12); re-read `is_active` and the TOTP fields — an inactive account or one without active TOTP is refused; read the account's active link and the subject's active link (BD-19): the same pair is a no-op, another active link of the account is refused, the subject active on another account is refused with GOOGLE_LINK_CONFLICT; otherwise insert the row with `linked_by` = the account and its audit event; commit; GOOGLE_LINKED or GOOGLE_LINK_CONFLICT is written after it, the conflict alerting the Owner. A link of the same subject to another account that commits first turns this insert into 23505, answered as that conflict (LR-08). The account's own unlink, after password confirmation: under LK-03 a conditional update of the active row's unlink columns with reason SELF and `unlinked_by` = the account, the account's other sessions deleted last (LK-05), the audit event in the transaction and GOOGLE_UNLINKED after it. |
