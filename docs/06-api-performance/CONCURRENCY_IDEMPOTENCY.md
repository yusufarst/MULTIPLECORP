## 1. Conventions

- **Identifier families defined here:** D-CC (design decisions), TX (transaction classes), LR (lock rules), LK (lock classes, in canonical order), NX (command families outside AX-01–37), FU (first-use rows), GU (guard rules), ST (stale-state mechanisms), CI (command identity), BD (business duplicates), SQ (failure mapping), RY (retry and timeouts), NM (numbering), JB (jobs), RV (revocation), M (mandatory scenarios) and HO (handoffs). AX, C, the DATABASE §3.1 guards and H6 keep their owners' numbering.
- **Row-lock words:** an explicit row lock is always `FOR NO KEY UPDATE` — the mode an ordinary UPDATE takes. `FOR SHARE` and `FOR UPDATE` are never requested (D-CC-02; LR-03).
- **Anchor:** the one row whose lock a command must hold to change a row family ([section 4](#4-canonical-lock-order)). **Guard:** a GB row of [DATABASE §3.1](../04-architecture/DATABASE.md#31-guard-registry-and-reconciliation). **Born row:** a guard or state row inserted in the same transaction as the record it belongs to. **First-use row:** a row created on demand by whichever command needs it first ([section 8](#8-guards-and-first-use-rows)).
- **Outcome vocabulary** is [WORKFLOWS §1](../03-workflows/WORKFLOWS.md#1-conventions)'s and is not extended. COMMITTED, REJECTED and CONFLICT are the terminal outcomes of a command; PENDING and FAILED are the states of background work; a command that cannot be completed, or whose completion cannot be confirmed, for a technical reason is answered with the word FAILED, which is never a terminal outcome (the `TECH-021` note in WORKFLOWS §1).

## 3. Transaction and isolation model

**Isolation.** Every command runs at READ COMMITTED (D-CC-01). Its correctness rests on three documented behaviours: a locking read or an update that meets a row changed by an uncommitted transaction waits, then works on the newest committed version; every later statement of the transaction sees whatever committed before that statement began; and PostgreSQL checks a CHECK constraint on every row a statement writes. A command therefore locks its anchors, re-reads what it needs in statements issued *after* those locks are granted, and writes each guard once. No action uses SERIALIZABLE. Snapshot reads use REPEATABLE READ, READ ONLY (D-CC-11) and take no row lock.

**Where a stronger mechanism than a plain statement is needed, and why:**

| Mechanism | Used for | Why |
| --- | --- | --- |
| Explicit row lock on an anchor | every anchor of [section 4](#4-canonical-lock-order) before a precondition is read | a precondition over several rows — availability against a line remainder, the ten completion predicates, the pre-payment Kuitansi cap, the reservation-cut choice, an evidence resolution's lots, an account's current grants — cannot be a CHECK; it is true at commit only if nothing it read can change, which the anchor guarantees |
| One net guard statement per row | every guard of DATABASE §3.1 (GU-01) | PostgreSQL checks CHECKs per statement, so an intermediate state is never written |
| Conditional state transition | DRAFT → ISSUED, ACTIVE → ended, OPEN → APPLIED or STALE, an unused token → used, `lock_version` edits (GU-06) | the WHERE clause is re-evaluated on the newest row version, so a second transition of the same row matches nothing |
| Insert-or-lock | first-use rows (FU-01–FU-13) | two first users can neither both create the row nor both miss it |
| Savepoint after the identity row | every command (D-CC-05) | a refusal — decided by the application or raised by a CHECK, a unique key or a trigger — must leave a durable outcome and nothing of the action: no lock, no first-use row, no partial write |
| `SET CONSTRAINTS ALL IMMEDIATE` before the outcome is decided | every command with a deferred constraint trigger | DATABASE §25 runs the net-zero, snapshot-total, replacement-billing and void-with-replacement checks at the COMMIT of the action's transaction, so that their failure rolls the whole action back. This refines only the moment: they are forced as the last step before COMMIT, inside the savepoint, where a violation can be mapped and recorded — and the action's every row is still rolled back |
| Session-level advisory lock, taken before the transaction | evidence registration only (LK-28) | no row exists to lock before the first registration of a content hash or a type-free identity, and the FL-10 lookups the keys serialize stay outside the business transaction (H6-09) |
| REPEATABLE READ, READ ONLY | `ReconcileGuards`, exports, multi-query reports | one instant for facts and guards, and for every figure of one report |
| SERIALIZABLE | nothing | D-CC-01 |

**Short transactions.** A command transaction contains only the statements of its sequence. No network or external API call, PDF rendering, image processing, file upload or hashing, e-mail, password hashing or large report runs inside one (DATABASE §25; OB §31): files are validated and stored before the command, password hashes are computed before the identity transaction opens, and rendering, exports and notifications are durable rows or jobs started after commit ([section 15](#15-jobs-scheduler-and-queue)).

**Transaction classes.** Timeouts are set with `SET LOCAL` as the first statements of each transaction, so they are scoped to it and survive a transaction-pooling proxy. A page read is a single statement outside a transaction block, where `SET LOCAL` has no effect: its limit is the runtime role's default, which every other class overrides. P9 owns the values (HO-21).

| TX-02 | Cascade command | READ COMMITTED | 5 s | 30 s | commands of retry class B |
| TX-03 | Driven command | READ COMMITTED | 10 s | 60 s | commands run by a job or the import pipeline (class C) |

Every `lock_timeout` is longer than deadlock detection (LR-12).

## 4. Canonical lock order

### 4.1 Lock rules

| ID | Rule |
| --- | --- |
| LR-01 | Every row lock of a transaction is acquired in ascending canonical order: by class position (4.2), then by the class's key order. A transaction never acquires a lock that sorts before one it already holds. |
| LR-02 | A command takes all its row locks before its first write ([section 6](#6-command-envelope), phase B). Its writes touch only rows it has locked or rows it inserted itself. Token and session rows (LK-04, LK-05), and the export-request rows an access change withholds (RV-08), are locked by the statements that write them, the last ones of their transactions. |
| LR-03 | The only lock mode this design requests is FOR NO KEY UPDATE. PostgreSQL itself takes the stronger FOR UPDATE mode for a DELETE and for an UPDATE that changes a column of a unique index a foreign key could use: the delete of a draft row (DATABASE §19), of a session row (RV-05, RV-10) and of an expired `command_log` row (JB-08); the issue transition that writes a version's number columns (AX-15, AX-16, AX-22, AX-31); the attribution that writes a count finding's company (AX-07); a change of a draft project's client or company (NX-03; L-21); and a master edit that changes a unique key column — a code, a product's quantity scale, a bank account's identity, a numbering scheme's effective date (NX-01). Such a statement waits for every transaction that holds the FOR KEY SHARE lock of a foreign-key check on that row — one that has inserted a row referencing it — and no cycle can close through that wait. No row references a session or a `command_log` row. For a transactional row (a draft, a version, a finding, a draft project) every inserter of a referencing row holds that row's anchor (LR-06), so it cannot be running at the same time. For a master row the inserter is an ordinary command. One that locks the master row — a company at LK-06, a bank account at LK-07 — meets the master command at that position, before it has written anything. Any other inserter never locks it: it inserts in its write phase, when it waits for nothing any more, or as a first-use insert at LK-11 or later, after whichever of its project, actor and company rows it takes and — where the inserted row references a product — after that product's guard (LR-09); the master command holds only its identity, its actor's row, the master row and, for a product's policy, that guard, so such an inserter never waits for it. The identity row of LK-00, the one row inserted before any lock, carries no foreign key (CI-03), so it takes no such lock at all. A master command changes the key of at most one row. Every other foreign-key check never waits on a lock this design takes. |
| LR-04 | A row is locked once. No command requests a lock on a row it already holds, and the only strengthening of a held lock is PostgreSQL's own, named in LR-03. |
| LR-05 | Rows of one class are locked in ascending key order — the class's natural key wherever a row can be created on first use, so that existing rows and rows about to be created sort the same way, otherwise its id — either one statement per row or one statement per class that selects by key with ORDER BY on that key. The manual gives no guarantee about the order in which one statement acquires its row locks, so P8 verifies the plan of each multi-row lock statement (sort below the row-locking node) and the single-row form is used wherever that cannot be shown (HO-13). |
| LR-06 | Anchor ownership: a mutable row family is changed only by a command that holds the anchor 4.3 names for it. A command may therefore read, after locking an anchor, the rows that anchor owns and treat them as fixed until it commits. |
| LR-07 | A first-use row is created by insert-or-lock at its canonical position ([section 8](#8-guards-and-first-use-rows)); a command waiting inside that insert holds only locks that sort before the row. |
| LR-08 | A unique business-identity key is inserted only in the write phase, after every lock is held, in canonical table order and then key order. Each such key is covered by an anchor its competitor also locks ([section 11](#11-separate-duplicates)), so the competitor waits at the anchor and then finds the committed row; a wait inside a unique index can involve only transactions that wait for nothing else. |
| LR-09 | Every inventory movement locks the product guard row (LK-13) of each product it moves, whatever its net effect on that row, before any scope, lot, reversal, serial or reservation row of that product. A drop-ship confirmation moves no stock and locks the same row as the anchor of the product's serial policy and quantity scale (ST-09). |
| LR-10 | Every command scoped to one purchase — receipt, reversal, drop-ship confirmation, closure, cancellation, charge, cost correction, return, a disbursement against it and that disbursement's contra — locks that purchase's header (LK-21). |
| LR-11 | No lock is held across slow work ([section 3](#3-transaction-and-isolation-model), short transactions). |
| LR-12 | A lock wait is bounded by its class's `lock_timeout` (RY-04), which is longer than deadlock detection (1 s by default), so a real deadlock is reported as `40P01` and retried instead of timing out. |

### 4.2 Lock classes

Positions are total: a class with a lower number is always locked first. LK-00 is the envelope's own key, not a business anchor; **the project row is the first anchor, at position 1**. One class is no lock of a transaction at all: the registration keys of LK-28 are taken by the registration request before its transaction opens (FU-10). ### 4.4 Why the order cannot deadlock

1. **Row locks.** By LR-01 and LR-02 every transaction acquires its row locks in one total order. In any set of transactions waiting on each other, the one holding the highest-sorting lock is waiting for a lock that sorts higher still, which no member of the set that waits for a lower lock can hold — so no cycle exists. The check is mechanical over the declared lock sets of [section 7](#7-statement-sequences): every declared set is an ascending sequence of LK positions, so every "holds X while acquiring Y" edge points forward and the edge graph is acyclic ([P6_QUALITY_GATE](evidence/P6_QUALITY_GATE.md#static-validation) records the run).
2. **LK-00.** Only a duplicate of the same intent waits on a command's identity key, and it does so as its first statement, holding nothing.
3. **Implicit locks.** A foreign-key check takes FOR KEY SHARE, which conflicts with no lock this design requests. The statements for which PostgreSQL takes FOR UPDATE by itself wait only for inserters that wait for nothing their command holds (LR-03), and the identity row — the one row inserted before any lock — carries no foreign key.
4. **Unique keys and first-use rows** are waited for at their canonical position (LR-07) or under a common anchor (LR-08).
5. **Advisory locks** exist only at LK-28. A registration request takes its keys before its transaction, in (namespace, key) order, while it holds nothing else, and asks for no further key afterwards — so a request waiting for a key holds no row lock, and the keys can close no cycle with each other or with a row lock.
6. **One mode.** Every requested lock is exclusive, so no command holds a weaker lock and later asks for a stronger one on the same row (LR-04), and every waiter queues behind the holder.
7. **Jobs, sweeps and `GuardMaintenance`** take either one row or rows in the same order.
8. **Data-dependent sets** never acquire out of order: a required row that was not locked forces a restart ([section 5](#5-data-dependent-lock-set-protocol)).

Deadlock retry (SQ-13) remains the backstop for a defect or an implicit lock nobody foresaw. It is never the design: P9 alerts on every `40P01`, because each one is a defect to investigate (HO-25).

## 5. Data-dependent lock-set protocol

A lock set is **STATIC** when every row in it is named by the payload, by write-once references of rows so named (a line to its header, a header to its company and project, a lot to its product, a consumption to its lot, dispatch line and bearer, an application to its source and target, a return to its case), or by state that an anchor the action has *already locked* fixes (4.3) — that state is read only after the anchor is held, and the rows it names sort after the anchor. A lock set is **DATA-DEPENDENT** when at least one required row is named only by mutable state that no earlier-sorting held anchor fixes — typically a row that sorts *before* the state that names it: a project named by a consumption, a correction case named by a returned unit, a pending case named by a scope.

A data-dependent action follows exactly this protocol:

1. **Derive** the candidate lock set without locks, by ordinary reads.
2. **Lock** every currently known row in canonical order.
3. **Re-read and re-derive** the lock set under those locks.
4. **If the required set grew** — any required row is not held — release everything by rolling back and restart the whole action.
5. **Retry from the beginning** with the expanded set (the union of every set derived so far), within a bounded restart count (RY-03).

Rules of the protocol: the derivation of step 1 may be stale, which step 3 detects; holding a row that turns out not to be needed is harmless; a restart re-runs the whole envelope from phase A, authorization included, and rolls back the `command_log` row with everything else; restarts are counted separately from deadlock retries; no business row is written before step 3 succeeds (LR-02), so a restart discards only locks and first-use rows. Deadlock retry (`40P01`) is only a backstop, never the primary design. Every action — static ones too — re-reads under its locks the columns it used to derive a lock and restarts on a difference, so a reference this document treats as write-once is verified rather than trusted.

## 6. Command envelope

Every SF-CMD command — from a web request, the import pipeline, a job or any future integration — runs this envelope once per attempt (ARCHITECTURE §5). It is the template of every row of [section 7](#7-statement-sequences).

| Phase | What happens | SF-CMD step |
| --- | --- | --- |
| A — prepare (outside the command's transaction) | validate the allowed fields and formats, the `command_id` included (WS-01; CI-01); compute the payload fingerprint (CI-02); **replay probe** — one read of `command_log` by `command_id`: a terminal row sends the request straight to the replay table (CI-05) before any reference is resolved. Otherwise authorize in the controller (EN-01), resolve every reference by public identifier through the scope resolver (CS-04) — a reference that does not resolve is answered as not found only after the probe has been repeated, because the command in flight may be the one that removed it — and derive the lock set by unlocked reads. | B — lock | BEGIN; `SET LOCAL` the class timeouts (RY-04); insert the `command_log` row at LK-00 (CI-03) — if it already exists, follow the replay table (CI-05); SAVEPOINT; lock rows in canonical order from LK-01, creating first-use rows where due; once LK-03 is held, re-authorize (RV-01) **before any precondition is read**, so a denial discloses nothing | 6, 2, 3 |
| C — decide | read the clock once: that value is `recorded_at` for every row the command writes, so rows serialized by an anchor carry their lock order; if no log row existed, probe the command key of the primary fact (CI-08); re-read under the locks and re-derive the lock set ([section 5](#5-data-dependent-lock-set-protocol)); the cross-company grant or allocation authority of AZ-08 → REJECTED and routed (SQ-23); stale-state checks ([section 9](#9-stale-state)) → CONFLICT; preconditions and the in-transaction duplicate re-checks ([section 11](#11-separate-duplicates)) → REJECTED. A refusal keeps the state it read under the locks for its answer, rolls back to the savepoint, writes the terminal state on the `command_log` row and commits | 4, 5 |
| D — write | fact inserts; the guard statements (GU-01); conditional state transitions; the audit event; `SET CONSTRAINTS ALL IMMEDIATE`. A rule violation raised here (SQ-04, SQ-05, SQ-08, SQ-10) rolls back to the savepoint and is recorded as in phase C; the state it returns is re-read after that rollback | 7, 8, 9 |
| E — commit | update the `command_log` row to COMMITTED with its result identifiers and its expiry; COMMIT | 6 |
| F — after commit | dispatch jobs and invalidate caches; a failure here never changes the outcome (SQ-21) | 10 |

- **A terminal outcome is always committed by the transaction that holds the identity** (D-CC-05). The savepoint sits between the identity row and everything else, so a REJECTED or CONFLICT command commits its `command_log` row and nothing of the action — no lock survives the rollback, no first-use row is left behind, and a duplicate of the same intent stays blocked on LK-00 until the outcome is durable. Two refusals commit further rows, because an approved rule requires them: a stale count is marked STALE with its audit event (ST-03), and a refusal routed under AZ-08 leaves the audit events QS-20 reads (SQ-23). A denial or failure that ends the whole transaction (SQ-09, SQ-11–SQ-20, SQ-22) leaves no `command_log` row and is therefore never terminal, and a driven command records no refusal at all (CI-08).
- The response is sent only after the outcome is durable. An authorization denial (SQ-09, SQ-22) rolls the transaction back and answers as AZ-11 requires; it is not an outcome of the command and is not recorded.
- The audit event of the action is written in phase D and rolled back with the writes on a refusal (DATABASE §23); only the events of those two refusals are written after that rollback.
- `business_date` is an explicit field of every command payload and is part of the fingerprint, together with the fact of whether the user chose it or the form merely prefilled it (ST-08); a retry or replay after midnight or after a month boundary therefore carries the same date and draws from the same period (GAP-016).

## 8. Guards and first-use rows

| ID | Rule |
| --- | --- |
| GU-01 | Each guard row is written once per command, by one statement carrying the net signed delta of all its columns (DATABASE §1); deltas that several posting services contribute to one row are combined first (ARCHITECTURE §7). | GU-02 | The statement names its rows by their keys only and must affect exactly the rows it names. **Fewer is a failure, never a silent success:** the action ends FAILED with nothing committed and a guard-missing alert (SQ-18); it is not retried automatically and the row is never created at that point. |
| GU-03 | The row is already locked (LR-02) and its values were re-read under that lock, so the application refuses a broken precondition with the current state (SQ-02). The CHECK is the backstop, and a CHECK violation maps to the same rule (SQ-04). |
| GU-04 | Guard statements are issued in canonical order. |
| GU-05 | The `version` of a scope or product guard advances in the same statement by the number of the command's movements that have entries under that key, as DATABASE §3.1 defines it. |
| GU-06 | A conditional state transition names the expected state in its WHERE clause. Zero rows is the stale or duplicate outcome its sequence names (SQ-03), never success. |
| GU-07 | Only the posting service that owns a guard issues its statement (ARCHITECTURE §7). `GuardMaintenance` is the one audited exception; it follows the same order in a maintenance window (TX-08). |

**Born rows** are inserted with their record and have no creation race: the product guard with its product; the line guard with its line's first pin and the commercial guard with the project's first confirmation (AX-13) — a draft line or a DRAFT project, which may still be deleted, has none; the purchase-line guard with its line; the charge guard with its charge; the lot-cost row with its lot; the consumption guard with its consumption or confirmation line; the invoice guard with the invoice's issue; the source guard with its payment or opening credit; the money-fact guard with its money fact; the evidence guard with its evidence document or statement line; exposure rows with their case, and a founder's group rows with it; case counters with their case.

**First-use rows** are created on demand. **Insert-or-lock** means: `INSERT ... ON CONFLICT DO NOTHING` on the row's key, then a lock on the row — whichever transaction created it. A concurrent first user waits inside the insert for the other transaction and then finds the row. The row is inserted with the value its DATABASE §3.1 formula gives before the command's own effect — zero quantities, the reversed movement's original quantity, the share of the current allocation version — and the command's effect arrives only through its guard statement. It is created inside the command's savepoint, so a refused or failed command leaves none behind.

**A lost row is not a first use.** When the insert really creates the row, the command checks the proof in the last column before it goes on. **Reconciliation cadence (GAP-031).** `ReconcileGuards` (JB-06) stays verify-only and `GuardMaintenance` audited and manual. It recomputes all twenty-two registry rows of DATABASE §3.1 every night at 02:00 WIB, each family inside one TX-05 snapshot so facts and guard are compared at one instant; it also runs after every restore before the application reopens (P9), after a deployment that changes a posting service (P10), on the operator's demand, and after every P8 scenario. Where a §3.1 formula replays facts in recorded order — a serial's latest event, a group bound — the order is the `recorded_at` the envelope stamps after its locks are granted (phase C), with the row id as tie-break: PostgreSQL's default would take it at transaction start, before the lock wait, and two commands serialized by an anchor could then appear in the opposite order. A first-use row left at zero by a derivation that locked more than it needed equals its formula and is no difference. A difference is reported to the named operator and the technical log and never repaired, and it blocks nothing by itself: the operator and the Owner decide on `GuardMaintenance`. Between runs, GU-02, the first-use proof and SQ-04 are the immediate signals of a broken guard.

## 9. Stale state

| ID | Mechanism |
| --- | --- |
| ST-01 | **`lock_version`.** An editable row is changed only by an update whose WHERE clause carries the `lock_version` the client saw and which increments it; zero rows is CONFLICT with the current state (SF-CMD step 5; OB §32). The version of an **aggregate root covers its draft children**: any edit of a draft quotation revision's or invoice version's line, a draft document version, a draft project's line or a purchase line before its first effect bumps its root, so two Admins editing different lines of one draft still conflict and totals are never lost; a confirmation without a quotation carries the project's version for the same reason (AX-13). The affected-row count is read from the builder's update — never from a model save, which discards it. |
| ST-02 | **Conditional transitions.** DRAFT → ISSUED or SENT, ISSUED → VOIDED or SUPERSEDED, an application's or settlement's end, a count's or finding's close follow GU-06; a second transition of the same row is CONFLICT carrying the state already reached. |
| ST-03 | **Count staleness.** Applying a count locks the count, then the product and scope guards, and compares each `stock_count_scopes.basis_version` with the live scope `version`. Any difference returns CONFLICT: after the rollback to its savepoint the transaction commits, with that outcome, the count's conditional OPEN → STALE transition and its audit event — of authority class SYSTEM, because no authority was exercised. Staleness never reverts, so marking it needs no other lock. No stock row changes, so a count recorded against a superseded scope version never overwrites stock (C-33; L-14; GAP-009). A surplus attribution moves the scope version like any movement, so a count opened before it is stale too (AX-07). |
| ST-04 | **Force Complete snapshot hash.** The Owner's confirmation carries the hash of the blocker snapshot shown. After LK-01 is held, the three documents the transition row will store — the predicate snapshot, the unmet predicates and the residual obligations, with every amount and quantity as a decimal string — are recomputed, serialized canonically (sorted keys, no timestamps, a format version) and hashed; a different hash is CONFLICT with the current snapshot (AX-26; C-38). A changed amount therefore changes the hash even when the same records remain. |
| ST-05 | **Session expiry.** A form that was never sent is submitted after re-authentication as a new intent through SF-CMD step 5: it carries the `lock_version`, guard version or snapshot hash it saw and meets ST-01–ST-04 like any command (AU-07; GAP-015). A submission that may have reached the server keeps its `command_id` across the login (HO-02): if it had committed, the replay by the same account returns that outcome (CI-05); if it had not, it runs now with every check. |
| ST-06 | **Preconditions are not stale checks.** A quantity or amount precondition is re-read under its guard's lock and refused as REJECTED with the current state (SF-CMD step 4); CONFLICT is reserved for ST-01–ST-05, ST-07–ST-09, the business identities of [section 11](#11-separate-duplicates) and CI-05. The loser of a last-unit race is therefore REJECTED, deterministically. |
| ST-07 | **Disposition lists.** A command whose payload disposes of dependents — the applications and settlements of a payment contra, an invoice void or revision, a contra-fact — is compared, under LK-25, LK-26 and LK-27, with the dependents that exist now; if the payload does not cover exactly the current ACTIVE ones, the command is CONFLICT with the current list. |
| ST-08 | **A prefilled date that went stale.** The payload says whether the user chose its `business_date` or the form only prefilled it. A prefilled date that is no longer today (WIB) when the command first executes is CONFLICT with the current date, so nothing is backdated by a form left open across midnight or a month end (BR-DT-02); a chosen date is taken as it is (DIR-018), and a replay never re-evaluates either. |
| ST-09 | **Product policy.** Every movement, and every drop-ship confirmation, re-reads its product's serial policy and quantity scale after LK-13 is held; NX-01 changes them only under that lock (L-35). A difference from what the payload was validated against is CONFLICT with the current policy. Every other row that carries a quantity meets a changed scale through its scale key (DATABASE §1; C-09): that violation is CONFLICT with the current policy as well, and a change of scale that meets a row already using the old one is REJECTED (C-09). |

## 10. Command identity and replay

| ID | Rule |
| --- | --- |
| CI-01 | **Format.** Every SF-CMD command carries `command_id`, a UUID generated by the client for one user intent — version 4 or 7, in canonical lower-case form; any other version, the nil and max values and malformed text are refused in validation. Commands run by jobs, the import pipeline or a future integration use a deterministic UUID version 5 over a namespace per source and a stable name — `import:{batch public id}:{row number}:{import identity}`, `job:{type}:{durable row id}:{step}`, `event:{source}:{event identity}` (ARCHITECTURE §11; AX-28). A version 5 identifier is accepted only from those internal callers, never from a request, so no client can occupy the identity of a driven command. |
| CI-02 | **Fingerprint.** `v1:` followed by the SHA-256, in hex, of the canonical JSON of the command type, the company's and targets' public identifiers as submitted and the validated, typed payload (WS-01) — `business_date` and whether it was only prefilled (ST-08), the `lock_version`, guard version or snapshot hash it carries, override and confirmation reasons with the matches they acknowledge ([section 11](#11-separate-duplicates)) and file identifiers included. Canonical means UTF-8, keys sorted, no insignificant white space, strings in NFC, decimals as plain strings at their column scale, dates in ISO form, arrays in payload order, nulls explicit. The `command_id`, the CSRF token and presentation-only fields are excluded. No reference has to be resolved for it, so it is computed before the replay probe of phase A. The payload itself is never stored. The version prefix is stored with the fingerprint, and a replay is compared with the algorithm of the recorded version, which stays available for the whole retention period (HO-31). |
| CI-03 | **Placement.** The first statement of the command transaction is `INSERT INTO command_log (command_id, command_type, actor_user_id, company_id, payload_fingerprint, state) ... ON CONFLICT (command_id) DO NOTHING` with state IN_PROGRESS; the expiry is written with the terminal state (CI-07). The row records its actor and company as plain values without foreign keys (the `TECH-021` clause of DATABASE §4.13): it is the one row a command inserts before its locks, and a foreign-key check there would take a lock out of order (LR-03). IN_PROGRESS exists only inside the inserting transaction; other transactions ever see only COMMITTED, REJECTED or CONFLICT (the same clause adds the last). |
| CI-04 | **In-flight duplicate.** A second transaction with the same `command_id` waits inside that insert until the first ends, bounded by its `lock_timeout` and `statement_timeout`. If the first committed, the insert does nothing and CI-05 applies; if the first rolled back, the second inserts and executes. Beyond the wait horizon the duplicate is answered FAILED — nothing new committed, the same `command_id` retriable later (SQ-14). |
| CI-05 | **Replay.** When the row exists — found by the probe of phase A or by the insert of phase B — the checks of the replay table below run in order and the first that fails decides; nothing is executed again, and no reference of the payload is resolved before those checks, so a command that removed its own target still replays. The state a replay returns is resolved afterwards and is left out when it no longer resolves. |
| CI-06 | **What is recorded.** Only outcomes of SF-CMD steps 4–8: COMMITTED with the result's type and id, REJECTED with its rule code, CONFLICT with its cause code. Validation failures, authorization denials (SQ-09, SQ-22), FAILED attempts and the conflicts of CI-05 itself are not recorded. A new attempt after a terminal outcome is a new intent with a new `command_id` (HO-02). A deterministic identity is the one exception: only its COMMITTED outcome is recorded (CI-08). |
| CI-07 | **Retention.** `expires_at` is 30 days after completion — a design value that must stay longer than every real retry horizon: the 12-hour absolute session of AU-07 for a web intent, and the queue's retry window plus the failed-job retention of P9 for a driven one (HO-27). A daily purge (JB-08) deletes expired rows. After it, the per-table (`command_id`, `command_line_no`) keys of DATABASE §1 still stop a second effect (C-48; SQ-07). |
| CI-08 | **Deterministic identities** belong to a driver row — an import row, a durable job row, an inbox row — not to a person, and that row is the durable record of what happened to it. Only a COMMITTED outcome is recorded for such an identity: a refusal rolls the whole transaction back, the log row included, and the job writes it on the driver row (`import_rows.errors`; the inbox row), so that the row can be driven again once its cause is removed — a refusal recorded under an identity that cannot change would replay for the whole retention period. A re-drive of a row that did commit finds the driver row done, because AX-28 commits the import row's state with its facts. Behind that stands the probe every command makes when it finds no log row: it looks for the command key of its primary fact before any precondition is read, so a precondition that the first execution itself made false cannot turn a committed intent into a refusal. A hit is "already done" for a deterministic identity — the log entry is restored as COMMITTED with that result — and the CONFLICT of SQ-07 for a client identity. When a re-drive by another actor meets a recorded identity — an import resumed by a second Owner — the CONFLICT of the replay table means "recorded by another run": the job re-reads the driver row and continues, and nothing is disclosed to a person (DP-16). |
| CI-09 | **Outside the protocol.** Login, logout, password change, credential-link consumption and step-up confirmation are not SF-CMD commands: they never write `command_log`, and no secret ever enters a fingerprint. Their own sequences apply (RV-05, RV-10, H6-11). The upload of a file, an export request and a download are bookkeeping requests, not commands; the registration of evidence that follows an upload is a command (NX-07). |

The replay table of CI-05:

| Check | Result |
| --- | --- |
| The recorded actor is another account | CONFLICT carrying no state, no identifier and no hint of what the other command was (DP-16) |
| Same actor; re-authorization — scope and capability against current grants, for the recorded company and command type (RV-01) — fails | the AZ-11 denial any fresh command would get — not found or forbidden — disclosing nothing (DP-14, DP-16) |
| Same actor, authorized, but the command type, company or fingerprint differs | CONFLICT — the same intent with different content (SF-CMD step 6); nothing of the original is returned |
| Same actor and content, authorized | the recorded terminal outcome with the current in-scope state: COMMITTED with its result identifiers and the result's current projection, if the result still exists; REJECTED with the recorded rule code and the current state that rule concerns — the current matches of a duplicate warning included; CONFLICT with the recorded cause and the current state |

A replay commits nothing new. Its checks run in a transaction that holds the actor's row lock (LK-03) while it re-authorizes. A replayed credential-link issue returns the link's identifier, never the link, which is stored only as a hash (AU-11): the Owner revokes it and issues another.

## 11. Separate duplicates

A retry is the same `command_id`. A **separate duplicate** is a second intent for the same real event; it is caught by business identity where the event has one, and by a warning where it has none (SF-CMD step 6). Warnings stay warnings: each keeps exactly its approved override, none becomes a block and none is removed. A warning that is not overridden is REJECTED with its rule code and the matches the actor may see; the submission that carries the override or confirmation is a new intent and **names the matches it acknowledges**. Under the anchor, a current match the payload does not acknowledge is REJECTED again with the current matches, so an override given for one match never covers another that appeared meanwhile, and none can be sent blind with a first submission. Hard rules are evaluated before warnings. A command that commits with an override or a confirmation writes its audit event under the **acknowledged variant** of its action code — a registered code of its own — so that QS-21 and the Owner's queue find it by a typed column; DATABASE §17 keeps `metadata` out of every computation.

| SQ-23 | an effect the actor chose on another company's record, a loss whose bearer company is outside scope, or a new allocation, lacks the grant or the allocation authority that AZ-08 and XL-1 require | — | REJECTED with rule AZ-08 **and routed**: with the outcome, the transaction commits one audit event per affected company — the command's own company, where it has one, and every company on which the rule requires a grant or authority. Each event carries that company, the actor, the refused command's `command_id`, the target as its entity and the **routed variant** of the command's action code — a registered code of its own —, with authority class SYSTEM because no authority was exercised. Background work reports PENDING until its durable row reaches its final state and FAILED when its attempts are spent ([section 15](#15-jobs-scheduler-and-queue)). Constraint and trigger names carry their rule — the C-row, BR or L identifier — so the mapper never parses message text; a constraint without a registered rule is SQ-19. QS-20 lists the routed refusals of the last 14 days — a design value — as one item per actor, refused action and target, the newest first; an item is shown to an actor who has, for at least one of its refused commands, every company of that command's events in scope (PJ-13). It is a notice that ages out, not a task with a state of its own: whoever holds the grants acts through the normal command (PERFORMANCE section 7; HO-01).

## 14. Numbering concurrency

| ID | Rule |
| --- | --- |
| NM-01 | The counter row is the last lock of any action (LK-31), so it is held only for the statements that remain before commit; every business anchor, the project row included, is locked before it. |
| NM-02 | **Allocation.** Where NM-03 allows a first use, insert-or-lock the counter (FU-07) with `next_value` 1; then one statement increments the counter and returns the pre-increment value. Exactly one row must be affected. The row lock serializes issuers until commit. |
| NM-03 | **Period and seeds.** `period_key` comes from the version's `business_date` and the numbering scheme effective on that date, and is stored with the number; a YEAR key and a MONTH key never coincide. The allocator **fails closed**: an issue never creates a counter for a company and sequence type that has no seed boundary, and a numbering scheme creates no counter by itself. Every counter that is not created on first use is a **seed** that states its first number: the first number after every number of its period issued outside this database, whatever date that number carries, or 1 where there is none. Seeds come from the migration — AX-28 writes them from the import rows it names (DATABASE §24; HO-32) — and from the Owner's numbering command (NX-01), whose seeds carry the Owner's number and no import row; a counter created on first use carries no seed value. A granularity **governs** a period when a scheme of the type with that granularity is in force on some date of the period. An import seeds only periods whose dates all lie on or before its cutoff and, while the type has no seed boundary later than that cutoff, the periods into which the cutoff date falls under every granularity that governs them; AX-28 applies this rule again when it commits a seed row, and records a row the rule no longer admits as SKIPPED, with no counter and no refusal. For a company or a type that no import seeds, the numbering command writes the **start** of numbering: a seed for the period into which the day it is recorded falls, under every granularity that governs it; the start is refused before go-live, once the type has a seed boundary, and while a batch that is not ABORTED holds a VALID seed row of the type. The **seed boundary** of a company and type is a date: the latest of the cutoff dates of the batches, whatever their state, that hold a COMMITTED seed row of the type and the day of the start, which the start's own audit event records apart from its counters (DATABASE §23; HO-27) — so a counter lost by a defect cannot move it, and no other seed of the numbering command counts. It reads only typed columns, never `jsonb` (DATABASE §17) and never the counters: a seed row carries a registered `import_kind` for its sequence type, and the start's audit event carries the company and a registered action code for the start of its sequence type, as SQ-23 registers the routed variants of an action. It rests on what the migration and the Owner vouch for: once the type issues here, no number of it has been issued outside this database after its boundary, none carries a date after it, and each belongs to a period that contains its date or the day it was issued (HO-32; HO-39). **Go-live** is the day this database became the system of record, recorded once at the cutover (HO-32); until it is recorded, nothing is created on demand and the numbering command neither starts nor seeds. A period is **live** when it begins after the seed boundary — whatever its granularity and whichever scheme was in force on the dates it covers — and does not lie wholly before go-live. A counter is created on first use only for a live period; a period that is not live gets a counter only from a seed. Once the type has its boundary, the numbering command also seeds, with the first number the Owner states, any period of the type that has no counter and is not live — never one that lies wholly before go-live, which only the migration seeds (DATABASE §10), nor one for which a batch that is not ABORTED holds a VALID seed row. The numbering command — start, seeds and scheme changes — locks its company row (LK-06) and reads schemes, counters and batch rows under it; so does the Owner's commit request of a batch (NX-13), which is refused unless the batch holds a seed row for each period into which its cutoff falls under every granularity that governs it, unless the type's seed boundary is later than the cutoff. A seed that creates its counter first proves that no version issued here, live project or tombstone carries a number of its period at or above its first number, and an issue that finds no counter for a period that is not live first proves that none of them carries that period; a failed proof means a lost counter (SQ-18). Otherwise an issue that may create no counter is REJECTED (C-10) and never restarts at 1 over numbers issued outside this database, which are no rows here and which no UNIQUE key could notice: a document backdated into an unseeded pre-cutover period — a month inside a seeded year included — is REJECTED, and one backdated to before the start is REJECTED until its period is seeded. Once a type has its boundary, the numbering command refuses a scheme it adds or changes that takes effect before the day it is recorded, unless the scheme only extends the type's schemes backwards over dates no scheme of the type covered; it refuses a scheme whose first period is not live and has no counter, unless the same command seeds that period or the scheme is such an extension; and while a batch that is not ABORTED holds VALID seed rows of the type, it refuses a scheme that would govern the period into which that batch's cutoff falls while the batch holds no seed row for it. A change of granularity therefore starts a live period or continues a counter that exists or is being seeded, and a backward extension is admitted without a seed, its periods that are not live and have no counter REJECTED until they are seeded. This narrows DATABASE §10, which allows a counter on demand for every period from go-live on: no counter exists before the type has its seed boundary, and a period that is not live gets a counter only from a seed, never on demand. A seed that meets an existing counter may raise it, never lower it, and moves its seed value with it; it raises a defect alert when the counter has drawn a number and the new seed exceeds the counter's first number — its seed value, or 1 after a first use — because only then can a number have been reused; any other raise, the delta of HO-32 among them, is an ordinary, audited effect. For the verification of DATABASE §3.1, a counter's seed value is its migration seed, whoever wrote it. |
| NM-04 | A rolled-back issue consumes nothing: the increment is part of the transaction. A committed number is never reused: counters are never lowered, a void keeps its version row and a discarded project keeps its tombstone. |
| NM-05 | A backdated issue draws the next number of its own business-date period; chronology and number order may differ (DIR-018). |
| NM-06 | A double issue of one draft is one effect (BD-06). |
| NM-07 | **Committed values are reused, never recomputed.** Renders, retries, replays and sweeps read `business_date`, `period_key`, `sequence_no`, `revision_suffix` and `formatted_number` from the ISSUED version row (GAP-016). A BASE_SUFFIX revision takes its predecessor's suffix plus one under LK-30 and draws no counter; a NEW_NUMBER revision draws from the period of its own business date. |
| NM-08 | Project numbers use the same allocator with sequence type PROJECT at project creation. Discarding a DRAFT project writes its `retired_numbers` tombstone in the discarding transaction (L-37); the number stays consumed. |
| NM-09 | **Backstops:** UNIQUE (company, type, period, sequence number, revision suffix) and UNIQUE (company, type, formatted number) on versions, and the two UNIQUE keys of `retired_numbers`; a violation is SQ-19, because the allocator must never produce one. |
| NM-10 | Never `MAX(number) + 1`, never a PostgreSQL sequence for a business number, and no gapless promise: numbers are unique, monotonic per counter, append-only and never reused (C-10; BR-DOC-02). |

One main queue (OB §35). Durable database rows are the record of work owed; the queue, cache and limiter store (Valkey) is never a system of record. ARCHITECTURE §11 names the six jobs with a business-visible trigger and notes that a job performing business effects invokes actions with deterministic command identities; this register fixes the mechanics of those six and adds the three operational tasks the mechanisms need (JB-07–JB-09).

- **After-commit dispatch.** Every job is dispatched by the framework's after-commit mechanism from phase F; a job dispatched inside a transaction that rolls back is discarded. The payload is built at dispatch and carries identifiers only — job type, payload format version, the durable row's id, the actor and company context, the correlation id — never S3 values or secrets, and nothing sensitive is placed in the propagated log context (DP-09).
- **Scheduler.** One cron entry runs the scheduler each minute; every scheduled task uses overlap protection with an explicit expiry longer than its longest run. When the store is down a task cannot take its lock and does not run; the next minute tries again. A daily task that misses its minute that way is not caught up by the scheduler: P9 alerts on a day without a successful run (HO-25).
- **Store unavailable or emptied (GAP-013).** A committed action stays committed (SQ-21). The durable row — a rendition attempt, an export request, an import batch with its commit request — holds the work, and the sweeps (JB-02, JB-09) re-dispatch it when the queue returns, also after the store lost its contents: nothing on it is needed for correctness (PERFORMANCE SZ-09). Limiters follow H6-07. Sessions and every business fact live in PostgreSQL and are unaffected. Worker restarts on deployment use the cache and therefore need the store; P9 monitors it (HO-24).
- **Payload versioning (GAP-012).** Every payload carries a format version. A worker that meets a newer version than it knows releases the job back with a delay instead of failing it; a newer worker accepts the previous version for one release. Deterministic command identities make re-execution by either version safe. P10 sequences expand-only migrations, deployment and worker restart (HO-31).

## 16. Authorization and revocation races

| ID | Rule |
| --- | --- |
| RV-01 | **In-command re-authorization (H6-01).** Every command locks its actor's `users` row at LK-03 — after the project rows, before every other anchor — and, in statements issued after that lock is granted, re-reads the account's active flag, role, capability grants and company grants and re-checks scope, capability and prerequisites (AZ-05). It runs before any precondition is read, so a denial answers as AZ-11 and discloses nothing. The grant or allocation authority that AZ-08 and XL-1 require for an effect the actor chooses on another company's record is checked next, from the same re-read; failing it is not a denial but the REJECTED-and-routed outcome of SQ-23. |
| RV-02 | **Access changes.** A command that changes an account's role, capability grants, company grants or active state locks that account's row at LK-03 as well (TX-09). The lock is the same exclusive one a command of that account takes, so the change waits for the account's command in flight, and every later command of the account waits for the change and then reads the new state. Both queue on the row, so a stream of commands cannot keep the change waiting (D-CC-02). |
| RV-03 | **Linearization point:** the commit of the access-changing command. A command that held the account's row first ends before the change commits and was authorized when it ran; a command that arrives later waits and is then denied — "rejected on its next request" (AZ-03). A read request evaluates the committed grants once, at its start. |
| RV-04 | **Last active Owner (H6-02).** A command that would deactivate, or change the role of, an account holding the OWNER role locks the OWNER role row (LK-02) first, then the user rows, and counts the active Owners that would remain; zero is REJECTED (RG-09). Two such commands are serialized by LK-02. |
| RV-05 | **Deactivation (RG-10; H6-06)** is one transaction: the target's row locked, its grants revoked, its unused credential tokens revoked, its `sessions` rows deleted by `user_id` and its export requests withheld (RV-08). A request of that account arriving afterwards finds no session. A login that was being verified while the deactivation committed may still write a session row afterwards: the per-request check refuses it and deletes it (AU-09), and a reactivation deletes the account's sessions again in its own transaction, so no such row can come back to life. The per-request active check costs nothing extra: `is_active` is a column of the user row the session guard already loads. |
| RV-06 | **Idle timeout (AU-07; H7-13).** A background request — polling, deferred and visibility-triggered props, prefetch, thumbnails and previews — reads the session but never writes it, so the session row's last activity is the last user-initiated request and the 60-minute idle limit is the session lifetime itself; the 12-hour absolute limit is checked against the login time kept in the session. The framework's session middleware writes on every request, so this needs a variant of it that skips the write (HO-20). Background is decided on the server: thumbnail and preview routes are background by their route, any other GET only when the client marks it, and a request that is not a GET never is — so a background request can run no command. A download the user starts is a user-initiated request and extends the session like any other. |
| RV-07 | **Jobs (H6-04).** A job step re-resolves its actor's scope and capabilities when it starts and before each unit of work that opens a transaction of its own; a revoked or deactivated actor ends the job with nothing delivered (DP-09). An export reads inside one snapshot, where a later revocation cannot be seen, so it is checked before the snapshot opens and again at delivery (RV-08). |
| RV-08 | **Export delivery (DP-07).** A command that revokes a company grant or a capability, changes a role or ends an account's active state marks as WITHHELD, in its own transaction, every export request of that account that is PENDING, RUNNING or READY and not yet expired and whose recorded company set, capability set or masking context the account's grants no longer cover; P9's cleanup removes a withheld file at once (HO-29), and a job whose READY update the mark defeats removes the file it wrote (JB-03). The download is an ordinary GET and changes no business state (WS-04): it serves a request only in state READY, and only after comparing the requester's current company scope, capabilities and masking context with the recorded ones — so a request that escaped the mark is refused all the same, with the AZ-11 answer — and it writes the security event LG-02 requires. |
| RV-09 | **Replay (H6-03).** A replay re-authorizes as RV-01 before anything recorded is returned (CI-05). |
| RV-10 | **Credential changes (AU-09; AU-11).** The session keeps a keyed digest of the password hash its login verified, and the session guard compares it on every request with the hash on the account row it already loads; a mismatch ends that session. A password set or change therefore ends every other session exactly — also one that a login verified against the old password was still creating. The change itself is one TX-07 transaction under the account's row lock: re-read `is_active` and the hash the request had verified — a difference answers the generic failure, so two changes verified against one old password cannot both apply — set the new hash, revoke the account's unused links and delete its other sessions; the changing request then regenerates its session identifier (AU-06) and stamps its own session with the digest of the new hash. Login verifies outside any transaction within a slot of H6-12 and writes nothing to the account row unless the stored hash is due for a rehash (AU-02): the rehash is one conditional update of TX-07 that matches only while the row still holds the hash that was verified, so it can never write a hash of an old password over a newer credential. The session is stamped with the digest of the hash the login verified or, when its rehash update changed the row, of the hash that update wrote — never of a hash read afterwards. A rehash update that matches no row answers the generic failure: the stored hash changed while the login was being verified — by a password change, or by the rehash of another login of the account — and the user logs in again. One that cannot get the row within its lock timeout is left for the next login. A rehash changes the stored hash without changing the credential, so it ends the account's other sessions once: at the account's first login after P9 changes the hashing parameters, which is a planned event (HO-26). |
