Status: REVIEW | Updated: 2026-09-27 | Owner: Planning

## Coverage and failure gate

Every CAP-01–18 has at least one AC above; SHOULD refinements reference the same underlying behavior and denial safeguards. Every outcome O-01–07 is linked to scope and evidence through those IDs. P8 expands failure tests rather than replacing these contracts with a UI-only pass. [REFERENCE_COVERAGE](REFERENCE_COVERAGE.md) maps all 62 PDF capabilities and every flow branch to these contracts; GAP-024 tracks completion of the later rule/build-unit/test chain.

Missing data, file rendering, queue retry, network interruption, stale edits and expired sessions must yield truthful pending/failed/conflict outcomes with a safe recovery path. They must not report success that did not occur, duplicate effects that did occur, or leak private information while recovering. Detailed mechanisms remain later planning work.

These acceptance contracts are **not yet executed**. Release sign-off cannot occur while required document coverage, financial/access semantics, migration reconciliation, real-device suitability, independent backup or named operational responsibilities remain unresolved at their gates.

## Product completion conditions

CAP-18 / AC-21 preserve DIR-008 and PDF §§6.12–7 at product level. Every applicable condition must be true together; satisfying one never substitutes for another. Applicability and authorized exceptions must be evidenced. P2/P3 will refine rules and transitions; P1 does not grant a waiver, write-off or permission.

| Condition | Observable completion requirement |
| --- | --- |
| Fulfillment | Required goods/services fulfilled, or remaining scope formally cancelled/closed with valid authority and reason |
| Delivery | Required deliveries complete or formally closed; no unresolved discrepancy remains |
| Returns/corrections | No unresolved return/reversal/correction materially affecting project quantities, value or obligations |
| Generated documents | Required applicable company-issued documents are final/issued and available, not merely draft or failed rendering |
| Administration | Required client/admin evidence complete and valid, or validly waived with reason and authority; a company draft does not substitute for a required client original |
| Billing | Billing submission completed when applicable, distinguishable from issuing an invoice |
| Receivable | Balance resolved or explicitly approved formal handling recorded; outstanding debt never disappears because the project is closed |
| Stock | No incomplete relevant stock transaction or unresolved stock correction |
| Payment | No unresolved payment correction, reallocation or refund disposition affecting completion |
| Audit | Required actors, references, reasons and linked critical history exist and remain accessible to authorized reviewers |

GAP-022 owns who may waive/close/approve exceptional debt treatment and how completion is revalidated after later corrections. A diagram arrow and an all-green UI are insufficient authority.

## Feature, module and release completion obligations

The PDF's completion principles are required future evidence, not results from this planning review. Before calling any Build Unit DONE, explicitly evaluate all eight dimensions below. Applicable checks need deterministic evidence tied to the tested revision; genuinely non-applicable checks need a specific reviewed reason. A missing tool, insufficient time or a failed check is not N/A.

| Dimension | Minimum evidence obligation |
| --- | --- |
| 1. Business | Required capabilities, acceptance and material exception paths hold; policy decisions resolved |
| 2. UI/UX | Natural Indonesian, shadcn-based consistency, mobile and desktop usability/accessibility, loading/empty/error/conflict states |
| 3. Backend | Server validation, correct use-case behavior, meaningful failures and maintainable thin entry points |
| 4. Database | Correct migrations, required foreign/unique/check/not-null constraints, indexes and safe money/data representation |
| 5. Security/authorization | Authentication, capability/company/resource isolation, IDOR/BOLA, CSRF/session/cookie, XSS/SQL-injection/clickjacking and private-upload/download controls as applicable |
| 6. Concurrency/idempotency/integrity | Atomic effects, race/duplicate/retry protection, state preconditions, ledger/balance consistency, corrections and audit |
| 7. Performance/N+1 | Query evidence, bounded loading/pagination/search, appropriate indexes, no N+1 regression; measured targets when defined |
| 8. Automated verification | Pest/PHPUnit/backend and integration tests, relevant TestSprite flows, fresh CI, static analysis/style checks, frontend typecheck/build, regression and business UAT where applicable |

Each unit also updates documentation and CURRENT_STATE. Inventory dispatch explicitly covers authorization/company scope, valid barcode/product/project/quantity, sufficient stock, duplicates/concurrent dispatch, movement/balance/audit, reversal, N+1, responsive interaction and backend/concurrency/regression checks (AC-03/06/13/14/16/22). Payment covers normal/full/partial/DP/termin/overpayment, invalid amounts, isolation, duplicate/idempotent requests, correction/reallocation, audit, correct receivable and secured proof (AC-10/12/13/16). Invoice covers project/client/company/quantity/value snapshots, unique company/type/period numbering under concurrency, PDF/print, issue locking, revision/void history and access/tests (AC-01/08/12/13; GAP-007/016). These are minimum examples, not exhaustive tests.

A **module** is complete only when its required units and cross-module protections work together. Inventory must integrate identity/barcode, receiving/current balance/ledger/dispatch, location/minimum stock, adjustment/opname/returns/reversal, drop-ship, allocation/attribution, access, concurrency/idempotency and regression. A stock page alone does not pass. Billing/payment/documents must likewise reconcile together, rather than pass as disconnected screens.

**V1 release completion** requires full requirement→canonical spec→business workflow/rule→Build Unit→acceptance→required test traceability and all mandatory units DONE; golden normal flow and applicable branches passing; separate Owner and Admin Operasional UAT evidence; agreed migration reconciliation; company/permission isolation; inventory/payment integrity and critical race/retry checks; TestSprite regression and fresh CI; security and N+1/performance evidence; successful verifiable backup and timed restore; validated production configuration (debug off, secrets/access correct); successful human-operated deployment and post-deploy smoke checks. OS-01–06 remain the outcome index. No release gate has run in P1.

P8 owns the detailed DEFINITION_OF_DONE/test strategy; P10 owns module/release aggregation; P11 units and FEATURE_COVERAGE_MATRIX must preserve these obligations. Their files remain planned. Tool entitlement or cost problems must be surfaced before their gates (DEP-07), with any substitution reviewed under governance; no silent TestSprite omission and no vendor tool as the sole proof of correctness.
