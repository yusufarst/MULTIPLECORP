# The restore and its numbering raise

Status: REVIEW | Updated: 2026-11-21 | Owner: Planning

Written by [TASK-076](../../11-tasks/TASK-076.md) (PRQ-15). This page puts [BACKUP_RECOVERY §4](../BACKUP_RECOVERY.md#4-the-restore-procedure)'s steps 1–7 in order, with TASK-074's tooling ([BACKUP_RESTORE](BACKUP_RESTORE.md), which holds each command's detail). Each step names its source step. Where this page and the source differ, the source wins.

The operator runs it alone, from the recovery point chosen with the Owner, never over live writes (BK-08; BKR-05). A restore after a key compromise is not this procedure alone: it is [POST_INCIDENT_RECOVERY](POST_INCIDENT_RECOVERY.md) step 5, Scenario B.

| # | Step | Source |
| --- | --- | --- |
| 1 | **Stop writes.** Put MULTIPLECORP in maintenance mode and stop its queue workers and scheduler. The second application keeps running, untouched (BKR-07). No step flushes Valkey, which is never restored as truth (HO-23; JB-02; JB-09). | §4 step 1 |
| 2 | **Choose and verify** the recovery point with the Owner: run `backup:status`. If the chosen generation is corrupt or missing, the restore names the next older verified one, and `--fallback` takes it (BK-07). | §4 step 2 |
| 3 | **Restore into isolation.** Run `backup:restore`, with the generation's paired key installed in the one-off container ([BACKUP_RESTORE §4](BACKUP_RESTORE.md#4-the-restore-backup_recovery-4) steps 3–5). It restores into a new database and a new files' directory, never over the live ones and never into the second application's. A leaked key is never installed. The deployment's go-live file stays where it is and is never restored over or rewritten (NM-03). The live state is kept until the restore is accepted. | §4 step 3; BKR-08 |
| 4 | **Reconcile.** The restore's record shows every file row with its bytes, every byte file with its row, and each owed rendition rendered again from its issued snapshot, never reissued or renumbered (GAP-007). The operator and the Owner then check the latest payments, receipts and issued numbers against the business's own papers. | §4 step 4 |
| 5 | **Verify the guards.** The record shows `ReconcileGuards`' read of the restored database. A difference is reported to the operator and the Owner, never repaired silently (HO-28; GAP-031). | §4 step 5 |
| 6 | **Resume safely.** Point the stack at the restored database and files once the restore is accepted. Restart the workers and the scheduler, so that owed work restarts through its durable rows and sweeps, not from Valkey (JB-02; JB-09; HO-23). **The maintenance mode stays on until step 7 is done.** | §4 step 6 |
| 7 | **Raise, reopen and record.** Nothing is numbered again until the Owner's raise is done:<br>1. **Find the highest numbers.** The Owner records, per company, type and period, the highest number on the papers issued after the recovery point.<br>2. **Raise the counters.** On the numbering page (*Penomoran*, PG-061, "Raise Counters After a Restore"), the Owner raises each affected counter to the number after that one, or creates the live period's counter. This is TASK-021's command, run **once in this recovery, never lowering a counter**, and audited with the incident.<br>3. **Reopen.** Only then do MULTIPLECORP's users resume and the maintenance mode lift.<br>4. **Record the loss.** Write into the [private incident record](forms/INCIDENT_RECORD.md) the recovery point, the elapsed time and what was lost after it.<br>5. **Record the lost facts again.** They go through the ordinary commands under new numbers, and the papers' numbers go beside them in the private record (RBK-02; GAP-064; architecture challenge 12a). | §4 step 7; DIR-083 OE-11; NM-03; NX-01 |
