# Key-compromise incident

Status: REVIEW | Updated: 2026-11-21 | Owner: Planning

Written by [TASK-076](../../11-tasks/TASK-076.md) (PRQ-15). This is [INFRASTRUCTURE §7.2](../INFRASTRUCTURE.md#72-the-key-compromise-incident-runbook) as the operator works it, with AU-21, H9-14 and the tabletop's findings. Each step names its source step, and none adds a path, authority, role or bypass. Where this page and the source differ, the source wins.

It is run by the operator, or by the alternate of P9Q-14 once named (DIR-083 OE-03), never by an agent. Every action applies to MULTIPLECORP's environment alone.

| # | Step | Source |
| --- | --- | --- |
| 1 | **The alarm.** The operator learns of it from the alert channel ([MONITORING](MONITORING.md); HO-25) or finds the sign. Open the [private incident record](forms/INCIDENT_RECORD.md) and write these first: the detection time (WIB), the incident's type, its source, the environments possibly affected, its status (suspected), and the evidence, masked, with no key value or credential (TT-F03). Tell the client once the incident is confirmed or may affect the service or its data (TT-F02). | §7.2 step 1 |
| 2 | **The window's start.** Set it with the Owner, at the earliest the evidence allows. When the leak cannot be dated, use the leaked key's creation time in the [dated key register](forms/KEY_REGISTER.md); when several keys leaked, the earliest such time. Record it **once**: in the private record and as the command's `--window-start`. It is never guessed. An unregistered or ambiguous creation time is the first halt of [POST_INCIDENT_RECOVERY](POST_INCIDENT_RECOVERY.md) step 6 (TT-F04; TT-F05). | §7.2 step 2; AU-25 |
| 3 | **The inventory and the scenario.** Take stock of host access, network and firewall, credentials, logs, and access through the other application on the VPS. A binding to the private interface never proves there was no write access (TT-F07). Choose **Scenario A** only when the inventory excludes write access; otherwise choose **Scenario B**. In Scenario B the host goes out of service, which stops the second application too, so the client is told and involved without delaying containment (TT-F06; INF-07). Scenario B continues in POST_INCIDENT_RECOVERY step 5. | §7.2 step 3 |
| 4 | **Rotate before the command** (TT-F09). Put a new `APP_KEY` and new HMAC keys in the environment, and enter each in the key register. Then rotate every other secret of SX-01 the leak may have included: the database role credentials, the Valkey password, the Google client secret and any mail credential. List the leaked key among `APP_PREVIOUS_KEYS` only if the ciphertext inventory finds data that must survive. Retire it from that list as soon as every such ciphertext is re-encrypted ([KEY_ROTATION](KEY_ROTATION.md) steps 3–4). | §7.2 step 4; AU-21 |
| 5 | **Maintenance mode on every process** (TT-F10). Turn it on, without a bypass, on every web process of MULTIPLECORP. Confirm each one by a forbidden request answered as refused ([COOLIFY_DEPLOYMENT](../COOLIFY_DEPLOYMENT.md)). An unconfirmed process stops the run. | §7.2 step 5 |
| 6 | **The command.** Run `php artisan iam:key-compromise --window-start=<the recorded start, ISO 8601 with its offset> --operator="<name>"`. It follows AU-21's protocol (a)–(d): the opening sweep, the maintenance mode kept, every account processed (including accounts created during the run), then the closing sweep. It refuses to start or continue outside maintenance mode, and refuses any other window start on a restart. | §7.2 step 6 |
| 7 | **Lift the mode only when safe.** Lift maintenance mode only after the closing sweep, with every step verified and the security and recovery-readiness checks met. A failed step keeps the mode on and stops the run. | §7.2 step 7 |
| 8 | **MULTIPLECORP only** (TT-F11). The second application's data and credentials change only under its own incident procedure. | §7.2 step 8 |
| 9 | **Then recovery**: [POST_INCIDENT_RECOVERY](POST_INCIDENT_RECOVERY.md). | §7.2 step 9 |
