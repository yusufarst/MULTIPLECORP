# Owner-account recovery

Status: REVIEW | Updated: 2026-11-21 | Owner: Planning

Written by [TASK-076](../../11-tasks/TASK-076.md) (PRQ-15). This is [INFRASTRUCTURE §7.1](../INFRASTRUCTURE.md#71-the-owner-account-recovery-runbook) as the operator works it, with AU-14 and H9-07 and the tabletop's findings ([BACKUP_RECOVERY §6](../BACKUP_RECOVERY.md#6-the-tabletop-incident-recovery-exercise)). Each step names its source step, and no step adds a path, authority, role or bypass that the source does not state. Where this page and the source differ, the source wins.

It is run by the operator alone, never by an agent (SX-04). The command runs on the production host in a one-off container of MULTIPLECORP's image, never through a web route (H9-03). Its use is rehearsed on staging only (SM-19; TASK-081). It acts on MULTIPLECORP alone (INF-07).

| # | Step | Source |
| --- | --- | --- |
| 1 | **The last resort.** Recovery codes come first, then another active Owner; recovery is the last resort. A code that a sustained second-factor cooldown blocks counts as not usable (AU-05). Write into the [private incident record](forms/INCIDENT_RECORD.md) why neither can serve, which the command takes as `--reason` (K3). After a key-compromise incident command, recovery follows [POST_INCIDENT_RECOVERY](POST_INCIDENT_RECOVERY.md) instead. | §7.1 step 1; AU-20 b, d |
| 2 | **Identity in person.** Verify the Owner in person through the [private contact record of the Owners](forms/OWNER_CONTACT_RECORD.md). Never use contact details the application holds, or a session or e-mail that may be compromised (TT-F12). Write the verification into the private incident record before the command runs, because the command cannot check an identity (TT-F13). When the Owner is the operator, the record says so and claims no independent verification (TT-F15; DIR-083 OE-03). | §7.1 step 2 |
| 3 | **The audit trail first.** Check the account's removals during an open compromise window before any issue. A pending restoration run comes first ([POST_INCIDENT_RECOVERY](POST_INCIDENT_RECOVERY.md) step 2). | §7.1 step 3; H9-07 |
| 4 | **The command.** Run `php artisan iam:owner-recovery-link <the account's e-mail> --operator="<name>" --reason="<why>"`. It issues an OWNER_RECOVERY link only for an active account holding the OWNER role. It never sets, reads or reveals a password or a TOTP secret. Its events record the host account and the stated name. **During a key-compromise run, until its recovery ends,** a link without a confirmer goes only to an account that held the OWNER role and was active at the recorded window start. For any other OWNER account, add `--confirmer=<the recovered pre-window Owner's e-mail>`: that Owner confirmed the account in the review, in person, never through the account being recovered, and the confirmation is written into the private record. The command checks the confirmer's standing. | §7.1 step 4; AU-14 |
| 5 | **The hand-over.** The Owner is present and opens the link on the Owner's own device. The link travels outside the application. It is never written into a log, a ticket, the private record or the repository. | §7.1 step 5 |
| 6 | **The use.** Setting the password clears the TOTP secret and the recovery codes, ends every session, revokes the other unused links and unlinks Google. The Owner enrols TOTP at once. | §7.1 step 6; AU-20 e |
| 7 | **The alert and the record.** OWNER_RECOVERY_LINK_ISSUED alerts three parties: the operator; the Owner, through a channel the operator does not solely control once one exists, otherwise by the in-app notice at the next login; and the confirmer it names ([MONITORING](MONITORING.md)). The private record holds the time, the account, the reason, the confirmer, the link's issue and use, and the result. It never holds the token. | §7.1 step 7; LG-07; H9-06 |
