## 1. Conventions and principles

- **Identifier families:** AU (authentication, sessions, credentials), EN (enforcement), WS (web and input), FL (files), LG (audit and security logging), SX (secrets, production, supply chain), TM (threats), D-SEC (design decisions), H6–H9 (handoffs to P6–P9). PERMISSIONS_MATRIX identifiers (AZ, RG, CS, PJ, RD, XL, OD, DP, D-PM, W4) are cited, not redefined.
- **Principles:** assume the database, a backup or a device can leak (OB §25); deny by default; least privilege; fail closed — an unavailable dependency never grants access; defence in depth — every control has a second line; no security through obscurity — public identifiers are unguessable but never sufficient (DATABASE §16); no control changes approved visibility, responsibilities, cost or scope (CHANGE_CONTROL Level 1).

## 2. Authentication, sessions and credentials

| ID | Control | Grounds |
| --- | --- | --- |
| AU-01 | **Accounts:** one individual account per person, identified by a normalized (trimmed, lower-case) e-mail address; no self-registration, shared, generic or service login account; created only by the Owner (PERMISSIONS_MATRIX OD-01). | BR-XC-02; WF-ACC-02; OB §17 |
| AU-02 | **Password hashing** (D-SEC-01): the framework hasher only — no custom hashing, manual salt or reversible storage. Driver `argon2id` with parameters at or above the OWASP minimum (≥ 19 MiB memory, ≥ 2 iterations, parallelism 1), tuned by P9 to about 0.25–0.5 s per hash on the VPS within its memory budget (H9-11). `bcrypt` only if the runtime lacks Argon2id, with work factor ≥ 12 and passwords longer than 72 bytes **rejected**, never truncated. Hash-algorithm verification and rehash-on-login stay enabled; because verification rejects a hash of another algorithm, a later driver change — the bcrypt fallback replaced by Argon2id — is a planned migration (verification relaxed only for a rehash-on-login window, or new credential links issued), never a silent switch (H9-11). No pepper in V1. | OB §24, §25; DATABASE §28; REF-001 |
| AU-03 | **Password policy** (D-SEC-06): at least 15 characters (NIST SP 800-63B-4 single-factor minimum; V1 has no second factor), at most 128; any printable Unicode and spaces, normalized to NFC before hashing and comparison; paste and password managers allowed; no composition rules; no periodic expiry; rejected when found in a blocklist of common and breached passwords or when it contains the account's own name or e-mail, the product name or a company name; a change is forced only when evidence shows the password is compromised. | NIST SP 800-63B-4; OB §24 |
| AU-04 | **Login without enumeration:** the same message, status and timing for an unknown account, a wrong password and an inactive account ("E-mail atau kata sandi salah" — final copy P7); when no account matches, the server still verifies against a dummy hash generated with the configured driver and current parameters (for example at boot), so neither timing nor an error reveals existence (H9-11). Success regenerates the session identifier and records LOGIN_SUCCEEDED; failure records LOGIN_FAILED with only a keyed hash of the submitted identifier (LG-03). | OB §24; AC-13 |
| AU-05 | **Throttling without lockout** (D-SEC-04): per normalized identifier + client IP, 5 failures per minute, then a cooldown that doubles up to 15 minutes; per client IP, 30 failed logins per 15 minutes, then a 15-minute cooldown; per identifier across IPs, no block — more than 20 failures in an hour raises a security event and an alert (LG-07). IPv6 addresses count per /64 prefix in these keys. No account is ever locked or disabled by failures, so no attacker can lock an account itself, the Owner's included; someone sharing the Owner's egress address — the office NAT or a carrier-grade NAT — can still delay logins from that address, which the Owner avoids from another network while the alert fires (section 8). A success clears its own key. Client IPs are trusted only from the local reverse proxy (WS-11). | OB §24; REF-001; GAP-013 |
| AU-06 | **Sessions** (D-SEC-02): server-side session store in PostgreSQL (the framework `database` driver), encrypted payload, one row per session carrying the user id so an account's sessions can be ended; cookie named with the `__Host-` prefix, Secure, HttpOnly, SameSite=Lax, path `/`, no domain, expiring when the browser closes. The session identifier is regenerated at login, at a password change and when a credential link sets a password; logout calls the framework logout, invalidates the session, regenerates the CSRF token and clears Inertia history. History is also cleared, together with the client's page and prefetch caches, at every other authentication boundary — the login page, the first response after login, every redirect caused by idle or absolute expiry, remote termination or deactivation, and the credential pages — or the client reloads the whole document there (H7-12), so history state saved under one session never renders after it ends. | OB §24; AC-13; WF-ACC-01 |
| AU-07 | **Timeouts** (D-SEC-03): idle timeout 60 minutes (sliding, where idle means no user-initiated request: background polling and automatic refreshes never extend a session, H7-13); absolute timeout 12 hours after login, checked on every request against the login time kept in the session. After expiry the account re-authenticates and an interrupted form is submitted again as a new intent through SF-CMD, whose stale-state check applies (WF-ACC-01; GAP-015); P7 warns before expiry and keeps unsent input on the client (H7-05). | GAP-015; SF-CMD step 5 |
| AU-08 | **No "remember me"** in V1 (D-SEC-03): no persistent login cookie, so the absolute timeout is real on shared office PCs and floor devices. | OB §24; D-SEC-03 |
| AU-09 | **Session termination:** deactivation ends every session of the account inside the deactivation command (PERMISSIONS_MATRIX RG-10); a password change or a password set through a credential link ends the account's other sessions; the authentication middleware rejects an inactive account on every request and deletes that session. A revoked grant or capability needs no session termination because authorization is re-evaluated on every request (AZ-03). | WF-ACC-02; AC-13 |
| AU-10 | **Concurrent sessions** per account are allowed (phone and desktop); the Owner (`users.manage`) sees each account's active sessions as a device summary with start and last activity — never a session identifier, payload or raw address (PERMISSIONS_MATRIX PJ-17) — and can end them. | CAP-14 mobile and desktop |
| AU-11 | **Credential tokens:** at least 256 random bits from a CSPRNG, kept only as a keyed hash in the application's credential-token store — an infrastructure table outside the 124 business tables of DATABASE §4, like the framework's session table, holding for each link its account, purpose (ONBOARDING, RESET, OWNER_RECOVERY), issuer, issue and expiry times and use or revocation (PERMISSIONS_MATRIX PJ-17) — bound to one account and one purpose, single-use with atomic consumption so two concurrent submissions cannot both succeed (H6-11), expiring after 24 hours (onboarding), 60 minutes (reset) or 30 minutes (Owner recovery), invalidated on use, on reissue, on deactivation and on any password change, and purged after expiry by the store's own scheduled job (H9-04). The framework's stock password broker, its token table and its path-token URL format are not used. | DATABASE §28 (reset tokens hashed); OB §24 |
| AU-12 | **Onboarding and reset under DEP-08** (D-SEC-05): the Owner creates the account and issues a credential link (`users.manage`); the link is shown once to the Owner as non-persisted flash data, never as a page prop kept in history, and the Owner delivers it out of band to the named person — in person, by phone, or as a message to the person's known number; the person opens it and sets a password under AU-03, so the Owner never learns it. The token travels in the URL **fragment**, which browsers never send in a request line or Referer and servers never log; on load the credential page removes the fragment from the address bar and history (`history.replaceState`) and keeps no token in page state; the page posts the token in the request body over HTTPS, and it is never flashed back after a validation error (WS-10); credential pages send `Referrer-Policy: no-referrer` and `Cache-Control: no-store`; consumption is throttled per IP and per token hash — a raw token is never a limiter key — and invalid, expired and used tokens get the same answer. Every issue is a business audit event and a security event; every use a security event. The account sees its own credential events, with a notice at its first login after any of them, and the issuing Owner receives an in-app notice when a link is used (AU-13; PERMISSIONS_MATRIX PJ-17), so a link consumed by anyone other than its holder comes to light. No e-mail, SMS or identity service is bought. A **self-service e-mail reset** is off in V1 and may be enabled only when P9 confirms a zero-cost sending channel (H9-06); it would answer identically for known and unknown addresses, throttle per address and IP, build links only from the configured application URL (WS-11) and follow AU-11. | DEP-08; WF-ACC-01; V1_SCOPE cost boundary |
| AU-13 | **Self-service** for an authenticated account: change its own password (current password required; AU-03; other sessions ended); see its own last successful login and its own credential events — link issued (when and by whom), link used (when, device summary), password set or changed — with a notice at the first login after any of them asking the person to tell the Owner if it was not them (H7-14); nothing else about accounts is self-editable, and the account's own profile, role, effective capabilities and scope are shown to it read-only (PERMISSIONS_MATRIX PJ-17). | BR-XC-02 |
| AU-14 | **Owner-account recovery** (WF-ACC-01; runbook H9-07): the authorized human operator verifies the Owner's identity in person and runs an audited console command on the production host that issues an OWNER_RECOVERY link (AU-11) for an account holding the OWNER role and refuses any other account; the Owner is present, opens the link on the Owner's own device and sets the password. The command never sets, reads or reveals a password; it records the operator's identity in a business audit event and in the security event OWNER_RECOVERY_LINK_ISSUED, which alerts the named operator and the Owner — the Owner through a channel the operator does not solely control when P9 confirms one, otherwise by an in-app notice at the next login (LG-07, H9-06). Trust in whoever holds host access is an explicit assumption: without such a channel an operator acting alone can recover the Owner account before the Owner is alerted (section 8). Agents never run it (SX-04). | WF-ACC-01; OB §37 |
| AU-15 | **Step-up confirmation** (D-SEC-12): `users.manage`, `permissions.manage`, `companies.manage` changes to bank accounts or identity assets, `import.commit` and credential-link issue require the account's password to have been confirmed within the last 15 minutes (the framework password-confirmation feature with its three-hour default shortened), so a stolen session alone cannot change access, money destinations or opening data; failed confirmations are throttled and logged (WS-12, LG-02). | OB §24 (high-risk Owner account) |
| AU-16 | **MFA** is not V1 scope (OB §24 "optional future MFA for high-risk owner account"). The login pipeline keeps a second-step seam for a zero-cost time-based factor; enabling or mandating MFA is an Owner decision (GAP-033). | OB §24 |
| AU-17 | **Prohibited:** impersonation or "login as", shared identities, self-registration and external API tokens (PERMISSIONS_MATRIX AZ-12, DP-04). | BR-XC-02; CHANGE_CONTROL Level 2 |

## 3. Enforcement architecture

| ID | Control | Grounds |
| --- | --- | --- |
| EN-01 | **Request pipeline**, in order: TLS termination (Nginx) → web middleware (encrypted cookies, session, request-forgery protection, WS-04) → authentication (active account, absolute timeout) → Inertia middleware (shared props, WS-07) → the route's capability requirement → controller: form request (allowed fields, WS-01; every reference resolved through the company-scope resolver, never by a global existence rule, so an out-of-scope reference fails exactly like a nonexistent one — PERMISSIONS_MATRIX CS-04) → policy (capability through the effective-capability resolver, scope through the company-scope resolver) → action (re-check of scope, references and capability; preconditions; one transaction; audit) → projection through prop resources (PERMISSIONS_MATRIX section 7). | ARCHITECTURE §2, §5, §8; AZ-01 |
| EN-02 | **Resolvers:** one effective-capability resolver and one company-scope resolver in the Identity module, read from the database on every request and memoized for that request only, used by every policy, gate, query class, job and action; gate hooks never grant by role name — the OWNER role simply holds every capability, and an OWNER_ONLY capability counts only through that role (RG-02). | AZ-02, AZ-03, AZ-04 |
| EN-03 | **Default-deny routing:** every route is in the authenticated group except login, credential-link pages, the minimal health check and, on staging only, the throttled and size-capped CSP report endpoint (WS-08); every authenticated route declares its capability; a route-audit test fails any route without one (H8-02). | OB §24; AZ-01 |
| EN-04 | **Query classes:** company-scoped query classes apply the scope resolver first; the pooled views use physical-only query classes that never select S3 tables; disabling global scopes or querying company tables outside query classes is prohibited and caught by architecture tests (H8-03). | ARCHITECTURE §8, §14; CS-07 |
| EN-05 | **Actions** are the one choke point for effects: web controllers, the import pipeline, jobs and any future API call the same action, which re-authorizes inside the command against current grants (P6 mechanism, H6-01). | ARCHITECTURE §5; AZ-05 |
| EN-06 | **No PostgreSQL row-level security in V1** (D-SEC-07). Company isolation rests on composite company keys (DATABASE §15, C-32), the scope resolver in every query class (EN-04), actions (EN-05) and P8 denial tests of every data path (H8-01). | DATABASE §28 (optional) |
| EN-07 | **Database roles:** web requests and workers use only the runtime role with the privileges of DATABASE §28; the migration/owner and administration roles are never reachable from them; if P9 provisions the optional read-only reporting role, an export produced through it still applies the requester's scope and projection (PERMISSIONS_MATRIX DP-07), and direct analysis through it is Owner or operator work, never an Admin path (H9-01). | DATABASE §28; OB §38; GAP-031 |
| EN-08 | **No third-party authorization package** (PERMISSIONS_MATRIX D-PM-07): framework gates and policies over the approved IAM tables. | ARCHITECTURE §19; P5 authorization §11 |

## 4. Web and input security

| ID | Control | Grounds |
| --- | --- | --- |
| WS-01 | **Allowed fields only:** each form request lists its fields with type, length, range and format rules; actions receive typed data objects built only from validated input; whole-request mass assignment and unguarded models are prohibited; the framework's strict-model checks (silently discarded attributes, lazy loading) run outside production. | OB §24; ARCHITECTURE §9, §19 |
| WS-02 | **Server-derived fields:** the company of an existing record, every actor column, `authority_class`, lifecycle states and transition kinds, numbers, snapshots, guard values, public identifiers, timestamps and outcomes are never accepted from a client. A client supplies only its `command_id`, the `lock_version` it saw (compared, never written), a `business_date` validated by SF-DATE — with equal Owner and Admin backdating authority (DIR-018; no capability gate) — references by public identifier (CS-04) and the company of a new root (CS-03). | DIR-018; SF-CMD; C-32 |
| WS-03 | **Lists and search:** whitelisted sort and filter keys, rejecting unknown ones; page size ≤ 100; opaque cursors re-validated; search input ≤ 100 characters, trigram search from 3 characters, LIKE wildcards escaped. | OB §24 (whitelist sort/filter keys) |
| WS-04 | **CSRF:** the framework `PreventRequestForgery` middleware in the web group — `Sec-Fetch-Site` origin verification with CSRF-token fallback — with no excluded route in V1; no GET request changes state; the Inertia client sends the XSRF token automatically. Origin-only mode may replace the fallback once P8 shows every supported browser sends the header (H8-08). | OB §24; AC-13 |
| WS-05 | **Cookies:** the session cookie of AU-06; the `XSRF-TOKEN` cookie Secure and SameSite=Lax (readable by the client by design); every cookie encrypted by the framework; no other cookie in V1. | OB §24 |
| WS-06 | **HTTPS and HSTS** (D-SEC-08): HTTPS only, with plain HTTP redirected by Nginx; HSTS introduced in stages by P9 — `max-age=300`, then one week, then one year with `includeSubDomains` once every subdomain serves HTTPS; no preload submission in V1. | OB §24 ("HSTS when HTTPS is stable") |
| WS-07 | **Inertia:** shared props hold only the account's display name, its own effective capabilities and granted companies (hints; the server decides), locale and generic flash text — never S2–S4 data, because shared data travels with every response; page props come from resources that list each field, never raw models; a prop needing a capability is not defined at all for an actor without it, so a partial reload (`only`/`except`) cannot obtain it; optional, deferred and closure props check their capability before evaluating and run the same scope-first query classes and resources as their page (PERMISSIONS_MATRIX DP-15); validation errors and flash messages never contain another record's data; history encryption is on for every authenticated page and history is cleared at every authentication boundary (AU-06); link prefetching is off on S3 and S4 pages. | PN-10 is planner analysis; PERMISSIONS_MATRIX DP-15 |
| WS-08 | **Response headers** (D-SEC-08), on every HTML and Inertia response: a Content-Security-Policy with a per-request nonce added by the framework's Vite integration — `default-src 'self'; script-src 'self' 'nonce-…'; style-src 'self' 'nonce-…'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'` — first in report-only mode on staging, with reports sent to a staging-only, throttled and size-capped same-origin endpoint (EN-03), then enforced; `'unsafe-inline'` for `style-src` only if P6/P11 show a vetted UI primitive injects styles at runtime, never for scripts, and `'unsafe-eval'` never in production; `X-Frame-Options: DENY`; `X-Content-Type-Options: nosniff`; `Referrer-Policy: same-origin` (credential pages `no-referrer`); `Permissions-Policy` denying camera, microphone, geolocation, payment, USB, serial and Bluetooth (USB scanners act as keyboards and V1 promises no camera scanning, D-05); `Cross-Origin-Opener-Policy: same-origin`; `Cross-Origin-Resource-Policy: same-origin`; `Cache-Control: no-store` on authenticated responses; no server or framework version banner. The application sets the nonce-bearing policy; Nginx sets the static headers and HSTS (H9-02). | OB §24 (headers, clickjacking) |
| WS-09 | **XSS and injection:** React escaping for all user text; raw HTML rendering prohibited unless passed through a vetted allowlist sanitizer (none planned in V1); user-entered URLs shown as text; PDF templates escape every value (FL-08); SQL only through query-builder bindings, raw SQL only with bindings and whitelisted identifiers; no user value in a shell command, file path or response header (FL-07, FL-08). | OB §24 (XSS, SQL injection) |
| WS-10 | **Errors:** `APP_DEBUG=false` and `APP_ENV=production` are release gates; error responses carry a generic message and the correlation id, never a stack trace, SQL, path, version or out-of-scope data (PERMISSIONS_MATRIX DP-20); details go to the redacted technical log (LG-04); password fields and credential tokens are never flashed back. | OB §24 ("APP_DEBUG=false") |
| WS-11 | **Proxies and hosts:** trusted proxies limited to the local reverse proxy, so throttling and log IPs cannot be spoofed through forwarded headers; trusted hosts limited to the configured domain; absolute links — credential links above all — built from the configured application URL, never from the request Host header. | OB §24; framework reset guidance |
| WS-12 | **Rate limits** on the framework limiter backed by Valkey (atomic increments; never business truth): login, credential-link consumption and step-up confirmation (AU-05, AU-12, AU-15); exact scanner lookups of barcodes and serials under a burst-sized limit of their own, separate from free-text search; password change 5 per 15 minutes per account; search 60 per minute per account; uploads 60 per hour and a daily byte budget per account; exports 10 per hour and 2 concurrent per account; commands 120 per minute per account; heavy reports 20 per 10 minutes per account. P6 tunes the numbers from measurement and fixes each limiter's behaviour when its store is unavailable — authentication, credential and step-up limiters fail closed (H6-07). | P5 authorization §7-K; OB §30 |

## 5. File security

| ID | Control | Grounds |
| --- | --- | --- |
| FL-01 | **Upload pipeline** (ARCHITECTURE §12), outside every business transaction: stream to temporary storage outside the web root → size check → content sniffing of the server-detected type (explicit `mimes`/`mimetypes` rules, which read content — never the broader `image` rule; `extensions` is always combined with them) → the purpose allowlist of FL-02, detected type and extension agreeing → the checks of FL-03–FL-06 → SHA-256 → generated storage key → the `file_objects` row in its own short transaction; the business command then references the file id. | OB §24, §31; DATABASE §22 |
| FL-02 | **Allowlist and limits per purpose:** evidence and proofs — PDF, JPEG, PNG, WebP, up to 20 MB; product images — JPEG, PNG, WebP, up to 5 MB; identity assets (logo, stamp, signature) — PNG, JPEG, up to 2 MB; import sources — UTF-8 CSV and XLSX, up to 20 MB; archive items (ARCHIVE) — PDF, JPEG, PNG, WebP, up to 20 MB. Evidence and archive items may also be **attachment-only office files** — DOCX and XLSX packages inspected structurally only — after the entry-count and uncompressed-size checks, the ZIP directory, content types, relationships and field codes are read with a hardened XML parser (no DTD, external entity or network access) — and rejected when they hold macros, ActiveX, OLE or embedded objects, external workbook links, external-target relationships other than hyperlinks, data connections or DDE fields; the application never previews, renders or evaluates them and serves them only as attachments (FL-07); a CSV is accepted only as an import source (FL-06). Everything else is rejected: SVG, HTML, scripts, archives other than OOXML, macro-enabled documents and executables. P8 device UAT confirms the formats real users hold (DEP-04, DEP-05); adding one is a Level-1 extension with its own checks. | OB §24; D-SEC-09 |
| FL-03 | **Images:** decoded only with an explicit allowlisted input format (JPEG, PNG, WebP) — every other coder or delegate, remote URL and indirect read disabled in the image library's policy, with memory, time and pixel limits (H9-12); dimensions are read from the header before the full decode, stopping decompression bombs (≤ 40 megapixels, ≤ 10,000 px per side); product images and identity assets are re-encoded during validation, so the stored object carries no EXIF/GPS or trailing payload; evidence photos keep their original bytes, whose metadata can be evidential, and are displayed through re-encoded, metadata-free previews derived by the image job (ARCHITECTURE §11). | OB §24 (EXIF/GPS, dimensions); D-SEC-09 |
| FL-04 | **PDFs:** header and structure check and the size limit; an uploaded PDF is never rendered inline from the application origin — it is served as an attachment (FL-07). | OB §24 |
| FL-05 | **Polyglots and active content:** displayed images are re-encoded; attachments carry nosniff and a sandbox policy; SVG is rejected; an upload whose checksum equals a stored rendition is flagged as a reproduction that can never satisfy a client original (FS-12; DATABASE §10). | OB §24; FS-12 |
| FL-06 | **Import files:** CSV and XLSX parsed as data only — no formula evaluation, external entity or macro; XLSX checked for uncompressed size and entry count before parsing; row and column limits; raw files private (S4), never in the repository. | CAP-15; DATABASE §24; ENGINEERING_PRINCIPLES |

## 9. Design decisions

| ID | Decision | Alternatives rejected |
| --- | --- | --- |
| D-SEC-01 | Argon2id through the framework hasher, bcrypt only as fallback with rejection above 72 bytes; no pepper in V1 — the framework offers no pepper, a custom wrapper is the custom hashing OB §24 forbids, and a lost pepper would lock every account (OWASP: pepper is defence in depth only). | bcrypt by default: silent 72-byte truncation risk; custom peppering |
| D-SEC-02 | PostgreSQL server-side session store, enabling per-account termination by user id; Valkey stays queue and cache only. | Valkey sessions plus a session-version check: another moving part for per-account termination and a second store to protect |
| D-SEC-03 | Idle 60 minutes, absolute 12 hours, no remember-me. | Long idle windows or remember-me: shared devices and the leak assumption |
| D-SEC-04 | Rate limits per identifier + IP and per IP, alerts per identifier, never lockout. | Account lockout after N failures (NIST's disable-at-100 included): lets anyone lock the Owner out |
| D-SEC-05 | Owner-issued, out-of-band credential links (onboarding, reset); self-service e-mail reset off until P9 confirms a zero-cost channel. | SMTP or SMS service: recurring cost; Owner-typed initial passwords: the Owner would know them |
| D-SEC-06 | 15-character minimum, blocklist, no composition or rotation. | 8–12 characters: below the current single-factor minimum; composition and rotation rules: rejected by NIST and a material change to user responsibilities |
| D-SEC-07 | No PostgreSQL row-level security in V1: authorization depends on per-user capabilities and grants that RLS would duplicate through per-request session variables across one runtime role shared by web and workers, adding a second policy language and failure mode; composite keys already stop cross-company references and P8 denial tests cover every path. RLS stays a compatible later defence (DATABASE §28). | RLS everywhere now |
| D-SEC-08 | Nonce-based CSP from the application; static headers and staged HSTS from Nginx. | Hash-based CSP (brittle with Vite builds); `'unsafe-inline'` scripts |
| D-SEC-09 | SVG rejected everywhere; displayed images re-encoded; evidence originals preserved with previews stripped. | Sanitizing SVG; stripping evidence originals (destroys evidential metadata) |
| D-SEC-10 | Authenticated controller streaming for every private file; no signed URL as authorization. | Signed URLs: bearer links that outlive revocation |
| D-SEC-11 | An isolated renderer: no network, no JavaScript, no shell, allowlisted assets. | Rendering from live URLs or remote assets: SSRF and non-reproducible documents |
| D-SEC-12 | 15-minute password step-up for the highest-risk Owner commands. | None (a stolen Owner session changes access and bank destinations); step-up everywhere (friction) |
| D-SEC-13 | Security-event catalogue with keyed hashing of identifiers and IPs. | Plain e-mails and IPs in logs (privacy; reversible hashes) |
| D-SEC-14 | MFA as a documented seam only. | Mandatory MFA: an Owner-level change (P5 authorization §9) |
