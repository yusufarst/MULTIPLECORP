## 1. Conventions and principles

- **Identifier families:** AU (authentication, sessions, credentials), EN (enforcement), WS (web and input), FL (files), LG (audit and security logging), SX (secrets, production, supply chain), TM (threats), D-SEC (design decisions), H6–H9 (handoffs to P6–P9). PERMISSIONS_MATRIX identifiers (AZ, RG, CS, PJ, RD, XL, OD, DP, D-PM, W4) are cited, not redefined.
- **Principles:** assume the database, a backup or a device can leak (OB §25); deny by default; least privilege; fail closed — an unavailable dependency never grants access; defence in depth — every control has a second line; no security through obscurity — public identifiers are unguessable but never sufficient (DATABASE §16); no control changes approved visibility, responsibilities, cost or scope (CHANGE_CONTROL Level 1).

## 2. Authentication, sessions and credentials

| ID | Control | Grounds |
| --- | --- | --- |
| AU-01 | **Accounts:** one individual account per person, identified by a normalized (trimmed, lower-case) e-mail address; no self-registration, shared, generic or service login account; created only by the Owner (PERMISSIONS_MATRIX OD-01). | BR-XC-02; WF-ACC-02; OB §17 |
| AU-02 | **Password hashing** (D-SEC-01): the framework hasher only — no custom hashing, manual salt or reversible storage. Driver `argon2id` with parameters at or above the OWASP minimum (≥ 19 MiB memory, ≥ 2 iterations, parallelism 1), tuned by P9 to about 0.25–0.5 s per hash on the VPS within its memory budget (H9-11). `bcrypt` only if the runtime lacks Argon2id, with work factor ≥ 12 and passwords longer than 72 bytes **rejected**, never truncated. Hash-algorithm verification and rehash-on-login stay enabled; because verification rejects a hash of another algorithm, a later driver change — the bcrypt fallback replaced by Argon2id — is a planned migration (verification relaxed only for a rehash-on-login window, or new credential links issued), never a silent switch (H9-11). No pepper in V1. | OB §24, §25; DATABASE §28; REF-001 |
| AU-03 | **Password policy — profile AICWDF-COMPAT-8** (D-SEC-15; D5; replaces the 15-character rule of the superseded D-SEC-06): 8 to 128 characters with at least one lowercase letter, one uppercase letter, one digit and one symbol; any printable Unicode and spaces, normalized to NFC before every check, hash and comparison; paste and password managers allowed; no periodic expiry; a change is forced only when evidence shows the password is compromised. A new password is refused when (1) it is in a locally bundled list of common passwords, checked first and without any network call — the list and its licence are chosen at implementation under DEP-07; (2) the breached-password range check finds it at least once — the k-Anonymity range query of the framework's `uncompromised` rule, by which only the first five characters of the password's SHA-1 hash leave the server, with response padding; or (3) it contains the account's own name or e-mail, the product name or a company name. The range check runs before any database transaction opens (H6-15), with a timeout of 5 s as a design value. **Failure behaviour:** when the range check gives no answer — a timeout, a transport error or an unsuccessful response — the password is not accepted: nothing is stored, a credential link stays unused, the person is asked to try again later and the security event PASSWORD_CHECK_UNAVAILABLE is written; repeated unavailability alerts the operator (LG-07). The framework's own verifier counts such a failure as "not compromised" (source), so the project's check recognizes the failure itself (H8-16). The profile is the Owner's selection, not a claim of NIST conformance; password hashing is AU-02's, unchanged. | D5 (DIR-037); AICWDF §4A.5; OB §24 |
| AU-04 | **Login without enumeration:** the same message, status and timing for an unknown account, a wrong password and an inactive account ("E-mail atau kata sandi salah" — final copy P7); when no account matches, the server still verifies against a dummy hash generated with the configured driver and current parameters (for example at boot), so neither timing nor an error reveals existence (H9-11). Success regenerates the session identifier and records LOGIN_SUCCEEDED; failure records LOGIN_FAILED with only a keyed hash of the submitted identifier (LG-03). A correct password completes the login only for an account without active TOTP that is not high-risk; an account with active TOTP meets the two-factor challenge (AU-16) and a high-risk account without it the enrolment-only session (AU-18), LOGIN_SUCCEEDED being recorded when the challenge succeeds or the enrolment is confirmed. A wrong, reused or stale code, a recovery code that does not match and an expired or voided challenge all get one generic answer with the same status; a failed Google sign-in gets one generic message that reveals nothing about accounts (AU-22). Every way of establishing a session — the login page, the in-place re-login after an expiry (ADMIN_FLOW IP-11, whose alignment P7 owes: H7-19) and Google sign-in — runs this same sequence; none is shorter. | OB §24; AC-13; D5, K1, K2 |
| AU-05 | **Throttling without lockout** (D-SEC-04): per normalized identifier + client IP, 5 failures per minute, then a cooldown that doubles up to 15 minutes; per client IP, 30 failed logins per 15 minutes, then a 15-minute cooldown; per identifier across IPs, no block — more than 20 failures in an hour raises a security event and an alert (LG-07). IPv6 addresses count per /64 prefix in these keys. No account is ever locked or disabled by failures, so no attacker can lock an account itself, the Owner's included; someone sharing the Owner's egress address — the office NAT or a carrier-grade NAT — can still delay logins from that address, which the Owner avoids from another network while the alert fires (section 8). A success clears its own key. Client IPs are trusted only from the local reverse proxy (WS-11). The two-factor challenge and every other step that checks a TOTP or recovery code are throttled the same way, keyed by account and client IP and by client IP, and never lock the account; more than 20 failed codes for one account in an hour raise a security event and an alert (LG-07). The Google redirect and callback are throttled per client IP. The project defines these limiters — Fortify throttles its challenge route only when a limiter is configured (source) — and, like the login limiter, they fail closed (WS-12; H6-07). | OB §24; REF-001; GAP-013; D5 |
| AU-06 | **Sessions** (D-SEC-02): server-side session store in PostgreSQL (the framework `database` driver), encrypted payload, one row per session carrying the user id so an account's sessions can be ended; cookie named with the `__Host-` prefix, Secure, HttpOnly, SameSite=Lax, path `/`, no domain, expiring when the browser closes. The session identifier is regenerated at login — at the password step before a two-factor challenge or an enrolment-only session begins, and again when the challenge succeeds —, when a Google sign-in reaches its challenge, at a recovery-code login, at every TOTP confirmation and disable (AU-16, AU-20), at a password change and when a credential link sets a password; logout calls the framework logout, invalidates the session, regenerates the CSRF token and clears Inertia history. History is also cleared, together with the client's page and prefetch caches, at every other authentication boundary — the login page, the two-factor challenge and enrolment pages, the Google callback, the first response after login, every redirect caused by idle or absolute expiry, remote termination or deactivation, and the credential pages — or the client reloads the whole document there (H7-12), so history state saved under one session never renders after it ends. Besides the password digest of RV-10, a session keeps whether and when it was established with TOTP and a keyed digest of the account's enrolment, its `two_factor_confirmed_at`; the session guard compares that digest on every request with the account row it already loads, so a session established under an enrolment that has since been confirmed anew, replaced, reset, disabled or voided ends, except the session that made the change, which is restamped in the same request (AU-16). | OB §24; AC-13; WF-ACC-01; D5 |
| AU-07 | **Timeouts** (D-SEC-03): idle timeout 60 minutes (sliding, where idle means no user-initiated request: background polling and automatic refreshes never extend a session, H7-13); absolute timeout 12 hours after login, checked on every request against the login time kept in the session. After expiry the account re-authenticates and an interrupted form is submitted again as a new intent through SF-CMD, whose stale-state check applies (WF-ACC-01; GAP-015); P7 warns before expiry and keeps unsent input on the client (H7-05). | GAP-015; SF-CMD step 5 |
| AU-08 | **No "remember me"** in V1 (D-SEC-03): no persistent login cookie, so the absolute timeout is real on shared office PCs and floor devices. | OB §24; D-SEC-03 |
| AU-09 | **Session termination:** deactivation ends every session of the account inside the deactivation command (PERMISSIONS_MATRIX RG-10); a password change or a password set through a credential link ends the account's other sessions; the authentication middleware rejects an inactive account on every request and deletes that session. A revoked grant or capability needs no session termination because authorization is re-evaluated on every request (AZ-03). A change of the account's TOTP enrolment — a confirmation, a replacement, a reset, a disable or a voiding — ends every other session of the account (AU-06, AU-16, AU-20); a command that makes an account high-risk ends all its sessions in its own transaction (AU-18); an unlink of its Google identity by the account holder ends its other sessions, and one by the Owner all of them (AU-24); deactivation also unlinks the account's Google identity (AU-24). Ending sessions never changes a Google link. | WF-ACC-02; AC-13; D5, D6, K1 |
| AU-10 | **Concurrent sessions** per account are allowed (phone and desktop); the Owner (`users.manage`) sees each account's active sessions as a device summary with start and last activity — never a session identifier, payload or raw address (PERMISSIONS_MATRIX PJ-17) — and can end them. | CAP-14 mobile and desktop |
| AU-11 | **Credential tokens:** at least 256 random bits from a CSPRNG, kept only as a keyed hash in the application's credential-token store — an infrastructure table outside the 125 business tables of DATABASE §4, like the framework's session table, holding for each link its account, purpose (ONBOARDING, RESET, OWNER_RECOVERY), issuer, issue and expiry times and use or revocation (PERMISSIONS_MATRIX PJ-17) — bound to one account and one purpose, single-use with atomic consumption so two concurrent submissions cannot both succeed (H6-11), expiring after 24 hours (onboarding), 60 minutes (reset) or 30 minutes (Owner recovery), invalidated on use, on reissue, on deactivation and on any password change, and purged after expiry by the store's own scheduled job (H9-04). The framework's stock password broker, its token table and its path-token URL format are not used. A credential link never creates an authenticated session and never bypasses TOTP: after setting the password the person logs in through AU-04's sequence and passes the challenge or enrols (AU-16, AU-18). Only an OWNER_RECOVERY link resets TOTP (AU-20 e). | DATABASE §28 (reset tokens hashed); OB §24; K3 |
| AU-12 | **Onboarding and reset under DEP-08** (D-SEC-05): the Owner creates the account and issues a credential link (`users.manage`); the link is shown once to the Owner as non-persisted flash data, never as a page prop kept in history, and the Owner delivers it out of band to the named person — in person, by phone, or as a message to the person's known number; the person opens it and sets a password under AU-03, so the Owner never learns it. The token travels in the URL **fragment**, which browsers never send in a request line or Referer and servers never log; on load the credential page removes the fragment from the address bar and history (`history.replaceState`) and keeps no token in page state; the page posts the token in the request body over HTTPS, and it is never flashed back after a validation error (WS-10); credential pages send `Referrer-Policy: no-referrer` and `Cache-Control: no-store`; consumption is throttled per IP and per token hash — a raw token is never a limiter key — and invalid, expired and used tokens get the same answer. Every issue is a business audit event and a security event; every use a security event. The account sees its own credential events, with a notice at its first login after any of them, and the issuing Owner receives an in-app notice when a link is used (AU-13; PERMISSIONS_MATRIX PJ-17), so a link consumed by anyone other than its holder comes to light. No e-mail, SMS or identity service is bought. A **self-service e-mail reset** is off in V1 and may be enabled only when P9 confirms a zero-cost sending channel (H9-06); it would answer identically for known and unknown addresses, throttle per address and IP, build links only from the configured application URL (WS-11) and follow AU-11. An Owner's TOTP reset of an account (AU-20 c, d) makes its password unusable and issues one new RESET link under these same rules. | DEP-08; WF-ACC-01; V1_SCOPE cost boundary; K3 |
| AU-13 | **Self-service** for an authenticated account: change its own password (current password required; AU-03; other sessions ended); enrol TOTP and replace its device, view its recovery codes after password confirmation and regenerate them with a current code, and disable TOTP only while the account is not high-risk (AU-16, AU-19, AU-20 a, f); link and unlink its own Google identity (AU-23, AU-24); see its own last successful login and its own credential and factor events — link issued (when and by whom), link used (when, device summary), password set or changed, TOTP enrolled, replaced, reset, disabled or voided, a recovery code used or the codes regenerated, a Google identity linked or unlinked — with a notice at the first login after any of them asking the person to tell the Owner if it was not them (H7-14, H7-18); nothing else about accounts is self-editable, and the account's own profile, role, effective capabilities, scope, TOTP status and linked Google e-mail are shown to it read-only (PERMISSIONS_MATRIX PJ-17). | BR-XC-02; D5, D6 |
| AU-14 | **Owner-account recovery** (WF-ACC-01; runbook H9-07; extended by K3 to reset TOTP): the authorized human operator verifies the Owner's identity in person and runs an audited console command on the production host that issues an OWNER_RECOVERY link (AU-11) for an account holding the OWNER role and refuses any other account; issuing changes nothing else. The Owner is present, opens the link on the Owner's own device and sets the password; using the link also clears the account's TOTP secret and recovery codes, ends all its sessions, revokes its other unused links and unlinks its Google identity with reason OWNER_RECOVERY and `unlinked_by` NULL (AU-20 e; AU-24) — no application account performs that unlink, and the operator has no application-user representation, none being created. The command never sets, reads or reveals a password or a TOTP secret; it records the operator's identity — the host account that runs it and the name the operator states, never a user row, `actor_user_id` staying NULL — in the business audit event of the issue and in the security event OWNER_RECOVERY_LINK_ISSUED, both naming the credential link by its store identifier, which alerts the named operator and the Owner — the Owner through a channel the operator does not solely control when P9 confirms one, otherwise by an in-app notice at the next login (LG-07, H9-06). The audit events of the link's use and of the unlink name the same credential link, so the unlink traces to the operator through the link and its issue event. By K3 the command is the last resort — the Owner's own recovery codes first (AU-20 b), then another active Owner (AU-20 d); the runbook uses it only when neither can serve, and the command records the operator's statement of why in the issue's audit event. Trust in whoever holds host access is an explicit assumption: without such a channel an operator acting alone can recover the Owner account before the Owner is alerted (section 8). ## 8. Threat model

Actors: an internet attacker; a Company-A-only Admin probing Company B; an Admin with ordinary (ADM) capabilities probing ADM+ or Owner-only actions; a deactivated or revoked account with an open session or a queued job; a thief of an unattended device; a malicious or careless uploader; an operator with host access, trusted by assumption (AU-14); a phisher relaying credentials and codes in real time; whoever holds a person's phone, Google session or recovery codes. **Count:** 72 threat scenarios, each with at least one control and one P8 proof obligation. Residual risks: the four the Owner accepted with K4 — an 8-character password is weaker against offline guessing after a database leak (TM-69; GAP-038), TOTP does not resist real-time phishing (TM-70; GAP-039), an Owner can be deceived into resetting an Admin's TOTP (TM-68; GAP-040) and operator abuse of the recovery command (TM-57; GAP-041); a password holder can enrol a device for a high-risk account before its person does, which the person's failed challenge and first-login notice reveal (TM-67); a phone holding both the person's Google session and the authenticator lets whoever holds it unlocked pass both steps until the loss is reported (TM-72) — a consequence of D6 and K2 as approved, for which no new acceptance is claimed here; Google-side changes are seen only at the next Google sign-in (AU-24); per-user global capability grants (GAP-032); a mis-typed evidence family exposes a company document only within its own company, and a company document wrongly uploaded as pool evidence stays visible to holders of `stock.view` and `evidence.view` because evidence bytes and versions are immutable (DATABASE §22) — prevention is the content rule and the upload confirmation, detection the Owner's review of every pool upload (PJ-08, H7-11); an attachment-only office file is opened outside the application under the desktop application's own protections, its formulas and hyperlinks kept because originals are evidence (FL-02); a credential link consumed by someone other than its holder lets that person act as the account until the holder or the Owner notices (AU-12, AU-13); someone sharing the Owner's egress address can delay logins from it (AU-05); a `stock.view` holder watching the pool over time sees when lots appear and their first remainders — inherent in the approved S1 availability — but never their company, kind, source or cost (PJ-01, PJ-03); whoever holds host access is trusted, and without a confirmed channel outside the operator's control an operator acting alone can recover the Owner account before the Owner is alerted (AU-14, SX-04); no runtime evidence exists until P8.

## 9. Design decisions

| ID | Decision | Alternatives rejected |
| --- | --- | --- |
| D-SEC-01 | Argon2id through the framework hasher, bcrypt only as fallback with rejection above 72 bytes; no pepper in V1 — the framework offers no pepper, a custom wrapper is the custom hashing OB §24 forbids, and a lost pepper would lock every account (OWASP: pepper is defence in depth only). | bcrypt by default: silent 72-byte truncation risk; custom peppering |
| D-SEC-02 | PostgreSQL server-side session store, enabling per-account termination by user id; Valkey stays queue and cache only. | Valkey sessions plus a session-version check: another moving part for per-account termination and a second store to protect |
| D-SEC-03 | Idle 60 minutes, absolute 12 hours, no remember-me. | Long idle windows or remember-me: shared devices and the leak assumption |
| D-SEC-04 | Rate limits per identifier + IP and per IP, alerts per identifier, never lockout. | Account lockout after N failures (NIST's disable-at-100 included): lets anyone lock the Owner out |
| D-SEC-05 | Owner-issued, out-of-band credential links (onboarding, reset); self-service e-mail reset off until P9 confirms a zero-cost channel. | SMTP or SMS service: recurring cost; Owner-typed initial passwords: the Owner would know them |
| D-SEC-06 | **SUPERSEDED** by D-SEC-15 (D5, DIR-037). Was: 15-character minimum, blocklist, no composition or rotation. | Was: 8–12 characters (below the current single-factor minimum); composition and rotation rules |
| D-SEC-07 | No PostgreSQL row-level security in V1: authorization depends on per-user capabilities and grants that RLS would duplicate through per-request session variables across one runtime role shared by web and workers, adding a second policy language and failure mode; composite keys already stop cross-company references and P8 denial tests cover every path. RLS stays a compatible later defence (DATABASE §28). | RLS everywhere now |
| D-SEC-08 | Nonce-based CSP from the application; static headers and staged HSTS from Nginx. | Hash-based CSP (brittle with Vite builds); `'unsafe-inline'` scripts |
| D-SEC-09 | SVG rejected everywhere; displayed images re-encoded; evidence originals preserved with previews stripped. | Sanitizing SVG; stripping evidence originals (destroys evidential metadata) |
| D-SEC-10 | Authenticated controller streaming for every private file; no signed URL as authorization. | Signed URLs: bearer links that outlive revocation |
| D-SEC-11 | An isolated renderer: no network, no JavaScript, no shell, allowlisted assets. | Rendering from live URLs or remote assets: SSRF and non-reproducible documents |
| D-SEC-12 | 15-minute password step-up for the highest-risk Owner commands. | None (a stolen Owner session changes access and bank destinations); step-up everywhere (friction) |
| D-SEC-13 | Security-event catalogue with keyed hashing of identifiers and IPs. | Plain e-mails and IPs in logs (privacy; reversible hashes) |
| D-SEC-14 | **SUPERSEDED** by D-SEC-16 (D5, DIR-037; K1, DIR-042). Was: MFA as a documented seam only. | Was: mandatory MFA, an Owner-level change (P5 authorization §9), which the Owner has since decided |
| D-SEC-15 | Password profile AICWDF-COMPAT-8 (D5): 8–128 characters with lowercase, uppercase, digit and symbol, NFC; the local list of common passwords first, then the breached-password range check, refusing the password when the check gives no answer; name, e-mail, product and company containment; no rotation (AU-03). | The 15-character baseline: superseded by the Owner (D5). A range check that passes on failure, as the framework's verifier does (source): it would accept a breached password whenever the service is down, weakening D5's blocking. The remote check alone: no protection without the network |
| D-SEC-16 | Mandatory TOTP for high-risk accounts, optional for the others (D5, K1): six digits, a 30-second period and one step of tolerance set explicitly; the durable per-account last step with a conditional update; enrolment held in the session until one correct code; no remembered device; Fortify-format recovery codes consumed under the account row lock (AU-16, AU-19). | TOTP for every account: the Owner made it optional for the others (K1). Passkeys, which Fortify offers: not decided by the Owner, so OFF. SMS or e-mail codes: recurring cost or no channel (DEP-08) and weaker. Fortify's cache-based reuse check: not durable and keyed by the code alone |
| D-SEC-17 | Laravel-native authentication (AICWDF §4A.1, §4A.7): Fortify for the login pipeline, the two-factor challenge, password confirmation and password update; Socialite for Google. Fortify policy: registration, password reset, e-mail verification, profile update and passkeys OFF; password update ON through a project action enforcing AU-03 and ending other sessions; two-factor ON with confirmation, password confirmation and an explicit window; password confirmation at 15 minutes; "remember me" never used; the login and two-factor limiters defined by the project (AU-05); project steps wherever Fortify's defaults fall short of AU-16, AU-18 and AU-19. | Hand-written authentication: more code for the same result. Sanctum, Passport or another authentication package: AICWDF §4A.7 excludes them without an API need. A hosted identity service: recurring cost and a dependency (DEP-08) |
| D-SEC-18 | The high-risk definition of K1 read from the resolver's inputs, an active grant counting whatever its prerequisites and a custom role's capability counting like a grant; a high-risk grant ends the account's sessions; the enrolment-only session; the per-request check ending a session not established with TOTP (AU-18). | Counting only currently effective capabilities: a re-granted prerequisite would silently restore an ADM_PLUS capability on a session without TOTP. Restricting a failing session to enrolment instead of ending it: an old session could enrol a device with only a confirmed password |
| D-SEC-19 | The reset and recovery contract of K3 with its common effects and six paths; the "in recovery" state derived from the audit timeline, not stored; key management through the previous-keys list, a re-encryption command and a voiding command (AU-20, AU-21). | An operator or system user row to carry recovery actions: forbidden (no application-user representation of the operator) and contrary to AZ-12. A stored recovery flag: a field beyond the four DIR-043 §7.9 allows. Clearing the old secret when a recovery code is used: the remaining codes and a found device would stop working before a new device exists |
| D-SEC-20 | Storage: four nullable TOTP fields on `users`, set and cleared together; the IAM table `user_external_identities` with the unlink contract, rows never deleted; no Google token stored; the pending secret, challenge, attempt marker and pending link kept only in the server-side session (AU-16, AU-22–AU-24; DATABASE §4.1). | A separate two-factor table: Fortify's columns already serve. Storing Google tokens: no use and a leak risk. Deleting unlinked rows: loses the history and the actor of each unlink |
| D-SEC-21 | Google sign-in and linking (D6, K2): the authorization-code flow with PKCE, `state`, a purpose-bound attempt marker and a `nonce` checked against the ID token; `openid email`; account selection on every sign-in; mapping by `sub` only; linking only by the holder with password confirmation and a current code, one-to-one, a conflict refused with an Owner alert; the TOTP challenge after every Google sign-in (AU-22, AU-23). | Automatic linking by a verified e-mail: Google documents that the e-mail is not an identifier, and it would hand an account to whoever controls a matching Google e-mail. Owner-performed linking: the Owner would need the person's Google sign-in. Google One Tap: a third-party script under the CSP and silent sign-in on shared devices |
