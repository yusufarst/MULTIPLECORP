## 1. Conventions and principles

- **Identifier families:** AU (authentication, sessions, credentials), EN (enforcement), WS (web and input), FL (files), LG (audit and security logging), SX (secrets, production, supply chain), TM (threats), D-SEC (design decisions), H6–H9 (handoffs to P6–P9). PERMISSIONS_MATRIX identifiers (AZ, RG, CS, PJ, RD, XL, OD, DP, D-PM, W4) are cited, not redefined.
- **Principles:** assume the database, a backup or a device can leak (OB §25); deny by default; least privilege; fail closed — an unavailable dependency never grants access; defence in depth — every control has a second line; no security through obscurity — public identifiers are unguessable but never sufficient (DATABASE §16); no control changes approved visibility, responsibilities, cost or scope (CHANGE_CONTROL Level 1).

| AU-01 | **Accounts:** one individual account per person, identified by a normalized (trimmed, lower-case) e-mail address; no self-registration, shared, generic or service login account; created only by the Owner (PERMISSIONS_MATRIX OD-01). | BR-XC-02; WF-ACC-02; OB §17 |
| AU-02 | **Password hashing** (D-SEC-01): the framework hasher only — no custom hashing, manual salt or reversible storage. Driver `argon2id` with parameters at or above the OWASP minimum (≥ 19 MiB memory, ≥ 2 iterations, parallelism 1), tuned by P9 to about 0.25–0.5 s per hash on the VPS within its memory budget (H9-11). `bcrypt` only if the runtime lacks Argon2id, with work factor ≥ 12 and passwords longer than 72 bytes **rejected**, never truncated. Hash-algorithm verification and rehash-on-login stay enabled; because verification rejects a hash of another algorithm, a later driver change — the bcrypt fallback replaced by Argon2id — is a planned migration (verification relaxed only for a rehash-on-login window, or new credential links issued), never a silent switch (H9-11). No pepper in V1. | OB §24, §25; DATABASE §28; REF-001 |
| AU-03 | **Password policy — profile AICWDF-COMPAT-8** (D-SEC-15; D5; replaces the 15-character rule of the superseded D-SEC-06): 8 to 128 characters with at least one lowercase letter, one uppercase letter, one digit and one symbol; any printable Unicode and spaces, normalized to NFC before every check, hash and comparison; paste and password managers allowed; no periodic expiry; a change is forced only when evidence shows the password is compromised. A new password is refused when (1) it is in a locally bundled list of common passwords, checked first and without any network call — the list and its licence are chosen at implementation under DEP-07; (2) the breached-password range check finds it at least once — the k-Anonymity range query of the framework's `uncompromised` rule, by which only the first five characters of the password's SHA-1 hash leave the server, with response padding; or (3) it contains the account's own name or e-mail, the product name or a company name. The range check never runs inside a database transaction — it finishes before the transaction that stores the password opens (H6-15) — and has a short timeout of 5 s, a design value. **Failure behaviour** (DIR-044 R-07): when the range check fails or does not answer within that timeout — a timeout, a transport error or an unsuccessful response — the remote check is skipped and the password is accepted only if it passes the local list, the containment rule (3) and every other rule of this profile; the security event PASSWORD_CHECK_SKIPPED records that the remote check was skipped, with the failure as its reason, and repeated skips alert the operator (LG-07). No offline copy of the breached-password corpus is required. The framework's own verifier reports a transport error to the exception handler, leaves an unsuccessful answer unreported and writes no security event, counting either as "not compromised" (source), so the project's check recognizes the failure itself in order to record it (H8-16). The residual — while the range service is unreachable, a breached password that passes the local list can be set — is accepted by the Owner (DIR-044 (f); GAP-046). The profile is the Owner's selection, not a claim of NIST conformance; password hashing is AU-02's, unchanged. | D5 (DIR-037); DIR-044 R-07; AICWDF §4A.5; OB §24 |
| AU-04 | **Login without enumeration:** the same message, status and timing for an unknown account, a wrong password and an inactive account ("E-mail atau kata sandi salah" — final copy P7); when no account matches, the server still verifies against a dummy hash generated with the configured driver and current parameters (for example at boot), so neither timing nor an error reveals existence (H9-11). Success regenerates the session identifier and records LOGIN_SUCCEEDED; failure records LOGIN_FAILED with only a keyed hash of the submitted identifier (LG-03). A correct password completes the login only for an account without active TOTP that is not high-risk; an account with active TOTP meets the two-factor challenge (AU-16) and a high-risk account without it the enrolment-only session (AU-18), LOGIN_SUCCEEDED being recorded when the challenge succeeds or the enrolment is confirmed. A wrong, reused or stale code, a recovery code that does not match and an expired or voided challenge all get one generic answer with the same status; a failed Google sign-in gets one generic message that reveals nothing about accounts (AU-22). Every way of establishing a session — the login page, the in-place re-login after an expiry (ADMIN_FLOW IP-11, whose alignment P7 owes: H7-19) and Google sign-in — runs this same sequence; none is shorter. | OB §24; AC-13; D5, K1, K2 |
| AU-05 | **Throttling without lockout** (D-SEC-04): per normalized identifier + client IP, 5 failures per minute, then a cooldown that doubles up to 15 minutes; per client IP, 30 failed logins per 15 minutes, then a 15-minute cooldown; per identifier across IPs, no block — more than 20 failures in an hour raises a security event and an alert (LG-07). IPv6 addresses count per /64 prefix in these keys. No account is ever locked or disabled by failures, so no attacker can lock an account itself, the Owner's included; someone sharing the Owner's egress address — the office NAT or a carrier-grade NAT — can still delay logins from that address, which the Owner avoids from another network while the alert fires (section 8). A success clears its own key. Client IPs are trusted only from the local reverse proxy (WS-11). **Second-factor limit** (DIR-044 R-01; it supersedes "throttled like login" of DIR-043 §7.4 for the second factor). *Flows covered:* every step that authenticates with a TOTP code or a recovery code — the sign-in challenge after a password or a Google sign-in, the recovery-code sign-in (AU-20 b), the current-code check of a device replacement (AU-20 a), viewing and regenerating recovery codes (AU-19), disabling TOTP (AU-20 f), Google linking (AU-23) and any other such step; *excluded:* the confirmation of an enrolment, whose code is checked against a secret just shown in the same session (AU-16), which stays under the per-account-and-IP and per-IP throttles only, takes no place in the count and writes no TWO_FACTOR_FAILED. *Count:* one failed-code count per account, shared across every client IP and every covered step, over a rolling **attempt window** of 15 minutes. Each submission takes its place in the count by one atomic increment before its code is evaluated and gives the place back only when its code is accepted, so the count holds failures alone and concurrent submissions cannot exceed it (H6-07). *Threshold:* the **fifth failed code** within the attempt window immediately invalidates the current challenge, or the pending step of the other covered flow, and starts the account-wide **cooldown** across all client IPs; the breach starts a new attempt window, its failures being carried by the escalation level. *Cooldown:* while it runs, every covered step of the account is refused without its code being evaluated — a refused recovery code is neither checked nor consumed — with the answer of a throttled login, and each refusal is recorded (TWO_FACTOR_COOLDOWN_REFUSED, aggregated per account and minute with their number, as H6-07 aggregates THROTTLED). *Progression:* the first breach within the escalation period gives a cooldown of 1 minute, the second 2 minutes, the third 4, the fourth 8, and the fifth and every later one 15 minutes, the cap; the cooldown always ends and is never a permanent lockout. *Decay:* a failure leaves the count 15 minutes after it was made; the **escalation level** is the number of breaches in the last 24 hours, a breach leaving it 24 hours after it occurred; the aggregated counts behind the signals of LG-07 are read from security events, which are never deleted or rewritten. *Success:* a successful second-factor authentication resets nothing — not the count, the escalation level, an aggregated count or any event —, so no reset caused by a success exists to be recorded. *Evidence and alerts:* each failure at a covered step writes TWO_FACTOR_FAILED with its path — PASSWORD at a sign-in challenge after a password, a recovery-code sign-in included; GOOGLE at one after a Google sign-in; SESSION_STEP, with the session's device summary (AU-10), at a step inside an authenticated session — and each breach writes TWO_FACTOR_COOLDOWN_STARTED with its level, its duration and the path that triggered it — password sign-in, Google sign-in, or a step inside an authenticated session — which alerts the Owner and the named operator with that path, the counted failures listed by path and the account's failure counts aggregated over the last hour and day, so the Owner can unlink the Google identity or end the abandoned session (LG-07; DIR-048). *Recovery codes* keep their single-use consumption under the account row lock (AU-19); this limit adds to it and never replaces it. *Defence in depth:* every covered step and the enrolment confirmation are also throttled per account and client IP and per client IP, like the login, and never lock the account. *Durability* (DIR-048 R2-02): the limit is a project-written atomic script on the limiter store, not the framework limiter, enforced from the stricter of two sources — the store, whose atomic operations bound concurrent submissions, and a durable floor read from the account's TWO_FACTOR_FAILED and TWO_FACTOR_COOLDOWN_STARTED security events (PERFORMANCE IX-19), which returns the time, submission identifier and place time of each failure counted since the later of 15 minutes ago and the latest breach, and the time, duration and identifier of each breach of the last 24 hours. The stricter of the two is taken in one atomic operation of the store: before a submission takes its place, every failure and breach of the floor that the store lacks is inserted at its own time — a failure identified by the submission identifier its event carries and a breach by the submission identifier of the failure that triggered it, which TWO_FACTOR_COOLDOWN_STARTED carries and by which the store keys its breach entry, so that none is counted twice —, unless the floor was read before the store's latest breach, in which case it seeds nothing into the new window; the place is then taken by an increment; and at a breach the operation empties the count, the breached window's failures, the fifth included, being those whose places were taken before the breach. Each TWO_FACTOR_FAILED carries its submission identifier and place time, and each TWO_FACTOR_COOLDOWN_STARTED the submission identifier of the failure that triggered it, in their whitelisted details, so no field is added. A restart, an eviction or a failover of the store therefore never shortens a cooldown, lowers the escalation level or reduces the count below the record, and a seeded entry leaves the count or the escalation level when its own time says so. The failure and breach events are written before the step answers, and a step whose durable floor cannot be read, or whose event cannot be written, is refused, so the limit fails closed. The store's keys for this limit carry no expiry of their own and hold time-stamped entries that the operation trims, so they are excluded from eviction; the store is sized never to evict — the framework's locks carry expiries —, its eviction policy being only the backstop (HO-24), and no failover store serves them. The window, the progression and the decay and success rules are stated the same way wherever the limit is described, and are P8 test obligations (H8-17). The residual is accepted by the Owner (DIR-044, extended by DIR-047; GAP-045; RISK-006): (e) anyone who can reach an account's second-factor step can deliberately delay that account's sign-in by triggering the account-wide cooldown of R-01 — a person who holds its password, a browser in which the person's linked Google account is still signed in, or an abandoned authenticated session within the password-confirmation window. The Google redirect and callback are throttled per client IP. The project defines these limiters — Fortify throttles its challenge route only when a limiter is configured (source) — and, like the login limiter, they fail closed: while the limiter store is unavailable, every covered step is refused (WS-12; H6-07). | OB §24; REF-001; GAP-013; D5; DIR-044 R-01; DIR-047; DIR-048 |
| AU-06 | **Sessions** (D-SEC-02): server-side session store in PostgreSQL (the framework `database` driver), encrypted payload, one row per session carrying the user id so an account's sessions can be ended; cookie named with the `__Host-` prefix, Secure, HttpOnly, SameSite=Lax, path `/`, no domain, expiring when the browser closes. ## 8. Threat model

Actors: an internet attacker; a Company-A-only Admin probing Company B; an Admin with ordinary (ADM) capabilities probing ADM+ or Owner-only actions; a deactivated or revoked account with an open session or a queued job; a thief of an unattended device; a malicious or careless uploader; an operator with host access, trusted by assumption (AU-14); a phisher relaying credentials and codes in real time; whoever holds a person's phone, Google session or recovery codes. Assets: company S3/S4 data, credentials, stock and money integrity, audit truth. Every threat names its controls and the P8 proof that must exist.
